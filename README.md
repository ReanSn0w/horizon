# Horizon

Horizon — консольный агент для работы с репозиториями через OpenAI Responses
API. Один запуск `resume` выполняет один ход агента, а история, рабочий контекст
и результаты инструментов сохраняются локально в Horizon home.

## Сборка и подготовка

Соберите бинарник версией Go из `go.mod` или более новой совместимой:

```sh
go build -o horizon .
```

Запустите Horizon: при первом рабочем запуске он создаст home и недостающие
стартовые файлы. Если конфигурация ещё не заполнена, команда агента завершится
кодом `2` и покажет путь к файлу до открытия редактора или чтения stdin.

```sh
./horizon
$EDITOR ~/.horizon/config.yaml
./horizon -m 'Посмотри проект'
```

В `config.yaml` заполните `provider.url`, `provider.key` и идентификатор модели
`models.chatting.model`. Проверьте `compact_threshold` для выбранной модели.
Пустые поля и прежние заглушки `replace-with-api-key` /
`replace-with-model-name` не допускаются при обращении к провайдеру.

По умолчанию используется `~/.horizon`. Для отдельного окружения передавайте
глобальный флаг `--home /path/to/home`; относительный путь считается от текущей
директории процесса. Например, `horizon --home ./agent-home` подготовит
конфигурацию и навыки в `./agent-home`.

Стартовая структура:

```text
<home>/
  config.yaml
  dialogs/
  skills/
    skill-creator/
      SKILL.md
```

Повторный запуск создаёт только отсутствующие ресурсы. Существующие файлы,
включая изменённый пользователем `skill-creator/SKILL.md`, не перезаписываются
при запуске или обновлении бинарника. Удалённый стартовый навык будет создан
снова. Новые каталоги получают права `0700`, стартовые файлы — `0600`.
Необязательный `AGENTS.md` можно добавить самостоятельно; реестр и файлы
сессий создаются хранилищем по мере использования.

Справка и ошибки аргументов не создают home. Локальные команды
`sessions list/create/read/delete` доступны без готового провайдера.
При создании конфигурации они выводят подсказку настройки в stderr.
Инициализация с уже готовой конфигурацией не печатает служебных сообщений;
stdout сохраняет контракт выбранного режима, включая `plain` и `jsonl`.

### Конфигурация

```yaml
mode: unit
default_model: chatting
models:
  chatting:
    model: replace-with-model-name
    reasoning: medium
    score: 100
    compact_threshold: 200000
provider:
  url: https://api.openai.com/v1
  key: replace-with-api-key
limits:
  max_model_requests: 128
  max_turn_duration: 120m
```

- `mode` на первом этапе принимает только `unit`: каждый процесс выполняет
  один ход.
- `default_model` — имя профиля по умолчанию. `--model` также принимает имя
  профиля, а не идентификатор модели провайдера.
- `model` — идентификатор модели у провайдера; `reasoning` — уровень reasoning;
  `score` — необязательная пользовательская метаданная.
- `compact_threshold` обязателен в каждом профиле и задаёт порог серверного
  сжатия в токенах.
- `provider.url` — базовый HTTP(S) URL. Horizon добавляет пути `responses` и
  `responses/compact`; `provider.key` отправляется как Bearer token.
- `max_model_requests` ограничивает попытки обращения к модели за ход, а
  `max_turn_duration` — общую длительность хода в формате Go (`30s`, `15m`,
  `2h`). Значение `0` отключает соответствующий лимит.

Конфигурация проверяется строго: неизвестные поля и некорректные значения
приводят к ошибке.

## Команды

Глобальные флаги `--home` и `--verbose` ставятся перед именем команды.
Без подкоманды Horizon запускает `resume`: работают `horizon`,
`horizon -m "Задача"`, `horizon --model chatting` и
`horizon --home /path/to/home -m "Задача"`. `horizon --help` показывает общую справку.

```sh
horizon models
horizon resume --model chatting -m 'Посмотри проект'
horizon resume --session SESSION_ID -m 'Продолжи задачу'
horizon sessions list
horizon sessions list --workspace /srv/project
horizon sessions list --active
horizon sessions create
horizon sessions create --fork SESSION_ID
horizon sessions read --id SESSION_ID --turns 4
horizon sessions compact
horizon sessions compact --id SESSION_ID
horizon sessions delete --id SESSION_ID
```

Без `--session` команда `resume` выбирает последнюю сессию текущего workspace,
а если её нет — создаёт новую. `sessions create --fork` копирует историю и
артефакты исходной сессии до последнего успешного хода.

### Ввод сообщения

Поддерживаются три способа, в таком порядке:

1. аргумент `-m` / `--message`;
2. перенаправленный stdin до EOF;
3. интерактивный редактор, если stdin является терминалом.

```sh
horizon resume -m 'Проверь тесты'
horizon resume < task.txt
cat task.txt | horizon resume
horizon resume
```

В редакторе `Enter` отправляет сообщение, `Shift+Enter` добавляет строку,
`Ctrl+J` служит переносимым запасным сочетанием, а `Ctrl+C` отменяет ввод.
Стрелки, Backspace, Delete и многострочная вставка поддерживаются. Ограничения
терминальных протоколов описаны в [docs/terminal-input.md](docs/terminal-input.md).

### Вывод

`--mode text` используется по умолчанию: готовый ответ выводится один раз
в stdout. Краткие статусы инструментов, начала хода и сжатия контекста идут
в stderr; потоковый текст модели и сырая статистика использования скрыты.

`--mode plain` предназначен для скриптов: при успехе stdout содержит только
итоговый ответ, stderr пуст. Передайте сообщение через `-m` или stdin до EOF;
интерактивный редактор в этом режиме не открывается.

```sh
horizon --mode plain -m 'Сделай обзор' > answer.txt
cat task.txt | horizon --mode plain > answer.txt
```

Перенаправление потоков не переключает режим автоматически. При ошибке
`plain` оставляет stdout пустым, пишет диагностику в stderr и завершается
ненулевым кодом. Выбор последней сессии и флаг `--session` работают во всех
режимах одинаково.

`--mode jsonl` пишет все события хода в stdout, по одному JSON-объекту на
строку, включая текстовые дельты и доступный `usage`. Диагностика CLI
остаётся в stderr:

```sh
horizon resume --mode jsonl -m 'Запусти проверки' > events.jsonl
```

Глобальный `--verbose` в `text` добавляет полные результаты инструментов,
пути к служебным логам и сырой `usage`. Потоковый текст модели остаётся
скрытым. В `plain` этот флаг не добавляет вывода.
Основные типы событий JSONL: `turn_started`, `progress`, `tool_started`,
`tool_completed`, `compaction_started`, `compaction_completed`,
`turn_completed`, `turn_failed`, `turn_cancelled`.

Коды завершения:

| Код | Значение |
| --- | --- |
| `0` | Успех, включая успешную операцию без изменений. |
| `1` | Ошибка выполнения, API, сети, файловой системы или состояния сессии. |
| `2` | Ошибка аргументов или конфигурации. |
| `130` | Отмена через `Ctrl+C`. |

Код, возвращённый `shell_exec`, хранится в результате инструмента и сам по
себе не становится кодом процесса Horizon.

## Workspace, инструкции и навыки

Workspace определяется реальным путём текущей директории: абсолютный путь
нормализуется с разрешением символических ссылок. Каждый подкаталог считается
самостоятельным workspace; корень Git автоматически не ищется. После переноса
проекта его новый путь образует новый workspace, а старые сессии остаются
привязаны к прежнему пути.

Перед каждым ходом Horizon читает `AGENTS.md` из home и из текущего workspace.
Родительские каталоги workspace автоматически не обходятся.

Навыки находятся в `<home>/skills/<каталог>/SKILL.md`. Файл начинается с YAML:

```markdown
---
name: review
description: Проверяет изменения в репозитории.
---

Инструкции навыка...
```

При инициализации устанавливается навык `skill-creator`. После настройки
провайдера можно поручить Horizon создание нового навыка:

```sh
horizon -m 'Создай навык проверки Go-проекта'
```

Агент загрузит инструкции создания навыков и сохранит результат в
`<home>/skills/<имя>/SKILL.md`, учитывая `--home`. Новый навык станет доступен
в каталоге со следующего хода; текущий ход использует снимок каталога,
подготовленный перед запуском.

Название и описание доступны модели постоянно. Полный текст загружается через
`skill_read`; возвращённый `base_dir` служит основой для относительных ссылок на
`scripts/`, `references/` и `assets/`. Такие ресурсы не загружаются
автоматически.

## Права и последствия выполнения

Horizon запускает файловые инструменты и `/bin/sh -c` с правами пользователя
ОС. Встроенной песочницы, списка разрешённых команд и сетевого фильтра нет.
Workspace задаёт исходный каталог, но не ограничивает доступ к другим путям.

Изменения файлов, удаления и внешние эффекты shell-команд автоматически не
откатываются. При таймауте или отмене Horizon завершает управляемую группу
процессов сначала через SIGTERM, затем через SIGKILL. Процесс, который успел
отделиться от этой группы, может продолжить работу и требует контроля
средствами ОС.

Перед запуском инструмента вызов сохраняется как `pending`, после результата —
как `known`. Если процесс оборвался между этими записями, исход становится
`unknown`: при продолжении модель получает указание проверить реальное
состояние перед возможным повтором.

## Хранение и восстановление

В `<home>/dialogs` хранятся реестр workspace, полные журналы сессий, рабочие
окна Responses API, записи сжатия, постоянные lock-файлы и каталоги
`<session-id>.artifacts` с полными stdout/stderr инструментов. `sessions read`
показывает журнал; сжатие меняет только рабочий контекст и не удаляет историю.

Форк получает независимую копию применимой истории, контекста и артефактов.
После этого источник можно удалить. Записи выполняются атомарной заменой файла;
при повреждении или утрате `workspaces.json` реестр восстанавливается из
валидных файлов сессий. Формат и порядок блокировок описаны в
[docs/session-format.md](docs/session-format.md) и
[docs/session-locking.md](docs/session-locking.md).

## Совместимость и проверка

```sh
go test ./...
go test -race ./...
go vet ./...
```

Автоматические тесты используют контролируемый Responses-совместимый сервер.
Проверка реального настроенного endpoint запускается явно:

```sh
HORIZON_API_CHECK=1 go test ./internal/responses -run TestConfiguredEndpointCompatibility -v
```

Подробности протокола находятся в
[docs/responses-protocol.md](docs/responses-protocol.md). Контракты семи
инструментов описаны в [TOOLS.md](TOOLS.md).
