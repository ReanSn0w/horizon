# Работа с Horizon

## Назначение и источники

Horizon — самостоятельный консольный агент на Go для работы с репозиториями
через Responses API. Один процесс выполняет один ход агента (`mode: unit`).
Сессии и результаты инструментов сохраняются локально; интерфейс рассчитан
на обычный терминал, скрипты и SSH.

Перед изменениями прочитай относящиеся к задаче код и тесты. Основные документы:

- `README.md` — запуск, конфигурация, команды и пользовательское поведение.
- `docs/TOOLS.md` — контракты инструментов.
- `docs/PLUGINS.md` — протокол подключаемых команд.
- `go.mod` — версия Go и зависимости.

Документация может отставать от реализации. При расхождении укажи его явно,
проверь код и тесты, не меняй поведение только ради старого описания.
Архитектурные контракты перечислены ниже; детали реализации проверяй
в соответствующих пакетах и тестах.

## Карта кода

| Путь | Ответственность |
| --- | --- |
| `main.go` | Передача потоков и аргументов в CLI, код завершения процесса. |
| `internal/cli` | Команды и флаги, ввод, терминальный редактор, режимы вывода и ошибки CLI. |
| `internal/bootstrap` | Подготовка home без перезаписи пользовательских файлов; встроенные стартовые ресурсы в `assets/`. |
| `internal/plugins` | Обнаружение установленных файлов и проверка метаданных без форматирования CLI. |
| `plugins/` | Исходники подключаемых команд репозитория; каждый плагин в отдельном подкаталоге. |
| `internal/config` | Строгая загрузка YAML, профили моделей, URL провайдера и лимиты. |
| `internal/instructions` | Снимок инструкций и каталога навыков на начало хода. |
| `internal/agent` | Цикл модели и инструментов, восстановление контекста, лимиты и сжатие. |
| `internal/responses` | HTTP/SSE-клиент, повторы запросов и типы Responses API. |
| `internal/decision` | Отдельный клиент Jev и политика оценки команд. |
| `internal/agenttool` | Схемы, проверка аргументов, исполнение и журналирование инструментов. |
| `internal/session` | Workspace, реестр, JSON-сессии, блокировки, форки и артефакты. |
| `internal/eventstream` | Общий формат событий выполнения. |
| `internal/e2e` | Проверки собранного бинарника, включая PTY и контролируемый HTTP-сервер. |

Сохраняй эти границы: форматирование CLI не должно проникать в хранилище,
HTTP-клиент или исполнители инструментов. Используй имеющиеся точки подмены
клиента, потоков, времени и редактора в тестах; не вводи глобальное состояние
ради удобства отдельной функции.

## Сборка и проверка

Команды выполняются из корня репозитория. Используй Go из `go.mod` или более
новую совместимую версию. Текущая реализация зависит от Unix: блокировки
используют `flock`, shell — `/bin/sh` и группы процессов.

```sh
go build -o /tmp/horizon-dev .
go test ./...
go vet ./...
```

После изменения Go-кода выполни `gofmt` для затронутых файлов. Для изменений
блокировок, отмены, процессов и параллельного доступа дополнительно запускай:

```sh
go test -race ./...
```

Для быстрой проверки можно сначала запустить тесты затронутого пакета,
например `go test ./internal/session`. При изменении поведения добавляй
проверку наблюдаемого результата или регрессии рядом с соответствующим кодом.
Для правок только документации проверь команды, пути и diff; новые тесты
не нужны.

Обычные тесты работают с временными каталогами и локальными тестовыми
серверами, без реального провайдера. E2E-тесты сами собирают бинарник.
Отказ среды разрешить localhost, PTY или запуск процесса отличай от дефекта
продукта и указывай как ограничение проверки.

Проверка реального API запускается отдельно:

```sh
HORIZON_API_CHECK=1 go test ./internal/responses -run TestConfiguredEndpointCompatibility -v
```

Она читает конфигурацию из стандартного `~/.horizon` и обращается к провайдеру.
Не включай её в обычные локальные проверки без задачи на проверку реального API.
Для ручных экспериментов с CLI используй отдельный временный `--home`, чтобы
не менять личные сессии и настройки. Не выводи и не коммить ключи провайдера,
пользовательский home, журналы сессий или артефакты инструментов.

## Контракты, которые нужно сохранять

### CLI и подготовка home

- Разрабатываемые здесь плагины размещаются в `plugins/<имя>/`; установленный
  файл хранится в `<home>/plugins/horizon-<имя>`. Дерево исходников репозитория
  не является источником автоматического обнаружения. При изменении хоста или
  плагина сохраняй протокол из `docs/PLUGINS.md`.
- Внешняя команда возвращает собственный код выхода; Horizon сохраняет его.
  Исполняемые файлы запускаются с правами пользователя ОС, включая запрос
  метаданных для справки или перед запуском.

- Отсутствие подкоманды означает `resume`. Глобальные `--home` и `--verbose`
  стоят перед подкомандой; `--model` выбирает имя профиля из конфигурации.
- `resume --access read|write|full` задаёт режим оценки команд на ход; по
  умолчанию `write`. Служебная `HORIZON_INHERITED_ACCESS`, переданная вложенному
  Horizon, имеет приоритет над флагом в обе стороны. Неверное значение — ошибка.
- Ввод выбирается в порядке: `-m` / `--message`, перенаправленный stdin,
  интерактивный редактор. Пустой ввод не должен изменять историю сессии.
- В `text` итоговый ответ выводится один раз в stdout, статусы — в stderr.
  В `plain` успешный ход выдаёт только ответ в stdout, не открывает редактор
  и не добавляет подробности по `--verbose`. В `jsonl` события идут в stdout
  без текстового оформления; диагностика CLI остаётся в stderr.
- Сохраняй коды завершения: `0` — успех, `1` — ошибка выполнения,
  `2` — аргументы или конфигурация, `130` — отмена через Ctrl+C.
- `horizon init` подготавливает home и выводит пути к `config.yaml` и
  `AGENTS.md`. Рабочие команды не создают home автоматически; при отсутствии
  конфигурации они предлагают запустить `init`. Справка и ошибки разбора
  аргументов тоже ничего не создают. Повторный `init` не перезаписывает
  пользовательские файлы. Новые каталоги имеют права `0700`, файлы — `0600`.
- `config.example.yaml` и `internal/bootstrap/assets/config.yaml` должны
  совпадать побайтово: это проверяет `TestEmbeddedResources`. При изменении
  конфигурации обновляй оба шаблона, валидацию и соответствующее описание.
- Диалоговый `provider` и обязательный для `resume` в режимах `read` и `write`
  `decision.provider` могут указывать на разных поставщиков. Для Jev указываются
  полный URL Decisions API, отдельный ключ и `decision.model`; пример есть в README. Старый
  пользовательский YAML `init` не переписывает, а отсутствие полей Jev должно
  давать адресную ошибку до создания хода в `read` и `write`. В `full` Jev не
  требуется.

### Workspace, инструкции и навыки

- Workspace — нормализованный абсолютный путь текущего каталога с разрешением
  символических ссылок. Корень Git не ищется; каждый подкаталог — отдельный
  workspace. Его ID — MD5 нормализованного пути.
- Перед ходом собирается снимок: вступление агента, `<home>/AGENTS.md`,
  `<home>/SOUL.md` при `soul_enabled: true`, каталог навыков и
  `<workspace>/AGENTS.md`. Родительские каталоги не обходятся.
- Навыки расположены в `<home>/skills/<каталог>/SKILL.md`. В инструкции
  включаются название и описание, полный текст загружается через `skill_read`.
  Ресурсы навыка разрешаются относительно возвращённого `base_dir`.
  Созданный во время хода навык появляется в каталоге со следующего хода.

### Управление навыками

- `skills list/validate/enable/disable` — локальные команды без обращения к
  провайдеру. ID — имя непосредственного каталога в `<home>/skills`, а
  `skill_read` принимает YAML-имя. Эти идентификаторы могут различаться.
- Перечисление не останавливается из-за повреждённого навыка. Проверка формата
  использует тот же валидатор, что загрузчик, но читает выбранный файл с диска
  независимо от других навыков. `ACTIVE` в таблице отражает настройку включения.
- Верхнеуровневый `disabled_skills` в `config.yaml` содержит ID отключённых
  навыков. Отсутствующее поле означает пустой список; старый конфиг не требует
  миграции. Отключённые файлы пропускаются до строгого разбора каталога.
- Изменение списка выполняется под отдельной постоянной блокировкой конфигурации,
  атомарно и с сохранением остальных значений, комментариев и прав доступа.
  При конфигурации через symlink изменяется разрешённая цель, сама ссылка остаётся.
- Отключение допускается для повреждённого навыка; включение проверяет формат
  и конфликт имени. Повторная установка того же состояния не переписывает файл.
- Снимок текущего хода не меняется. Новое состояние учитывается при следующей
  сборке инструкций как для `resume`, так и для `sessions compact`.
- Модель вызывает `horizon skills ...` через `shell_exec`. Исполнитель передаёт
  выбранный home в `HORIZON_HOME` и делает запущенный бинарник доступным как
  `horizon`, даже если его нет в `PATH`.
- Встроенный `skill-creator` использует CLI-валидацию; обновления бинарника
  по-прежнему не перезаписывают пользовательскую копию навыка.
- Встроенный `filesystem` описывает файловые операции через `shell_exec`.
  Повторный `init` устанавливает отсутствующий навык, сохраняя существующие
  пользовательские версии обоих навыков.

### Сессии и восстановление

- Хранилище — `<home>/dialogs/<workspace-id>/<session-id>.json`, артефакты —
  соседний `<session-id>.artifacts/`. Схему определяет `internal/session/types.go`;
  учитывай `format_version` и совместимость существующих данных при её изменении.
- JSON сохраняется атомарной заменой через временный файл в том же каталоге.
  Эксклюзивная блокировка ОС берётся на отдельном постоянном `<session-id>.lock`
  и удерживается весь ход. Занятая сессия возвращает ошибку сразу.
  Не удаляй и не заменяй lock-файл, в том числе при удалении самой сессии;
  наличие файла не означает, что блокировка удерживается.
- Сохраняй отдельные блокировки workspace и реестра; перед изменением порядка
  захвата изучи `service.go`, `lifecycle.go` и `files_unix.go`.
- Последняя сессия выбирается по `last_accessed_at`; отдельного указателя
  `last_session_id` нет. Повреждённый реестр восстанавливается по файлам сессий.
- До исполнения инструмент записывается как `pending`, после результата —
  как `known`. После аварийного завершения незавершённый вызов получает `unknown`.
  Ошибка сохранения вызова запрещает запуск; ошибку сохранения результата
  нельзя превращать в обычную ошибку инструмента, допускающую слепой повтор.
- Неудачные ходы остаются в журнале. Успешный checkpoint не заменяется ими,
  но `BuildInput` учитывает сохранённые данные последующих неудачных попыток
  и предупреждает о неизвестных последствиях. Не отбрасывай их безусловно
  и не повторяй автоматически операции с неизвестным исходом.
- Форк копирует историю до последнего успешного хода включительно и необходимые
  артефакты независимо от источника. Сжатие меняет рабочий контекст, сохраняя
  полный журнал.

### Responses API и инструменты

- Текущий транспорт — Responses API, включая SSE и `/responses/compact`.
  Сохраняй `store: false`, передачу зашифрованного reasoning и непрозрачных
  API items. Не пересобирай opaque items из сокращённой собственной схемы.
- Инструменты исполняются последовательно (`parallel_tool_calls: false`).
  После начала потока SSE запрос автоматически не повторяется; повторы
  учитываются в лимите попыток обращения к модели.
- Сохраняй строгие JSON-схемы и проверку аргументов в исполнителе. При изменении
  инструмента согласованно обновляй `registry.go`, `arguments.go`, обработчик,
  тесты и `docs/TOOLS.md`.
- Модель получает только `skill_read` и `shell_exec`. Файловые операции идут
  через `shell_exec` и ту же проверку Jev. История старых файловых вызовов
  читается, но новый вызов удалённого инструмента получает `unknown_tool`.
  Результаты инструментов имеют форму `{ok: true, data: ...}` либо
  `{ok: false, error: ...}`.
- `shell_exec` каждый раз запускает отдельный `/bin/sh -c` из workspace;
  `cd` не переносится между вызовами. Ненулевой exit code команды сохраняется
  в результате инструмента и сам по себе не является ошибкой запуска Horizon.
  Полные stdout/stderr сохраняются в артефактах, сокращённый вывод — в результате.
- Каждый `shell_exec` в режимах `read` и `write` перед исполнением требует
  успешного ответа Jev; недоступность, неполный ответ и отказ возвращаются
  модели без запуска команды.
  Jev получает команду и пути workspace и `HORIZON_HOME`, но не режим доступа
  или текст поручения; он оценивает только наличие локальной записи и записи
  вне этих каталогов. Horizon применяет режим к ответу: `read` не допускает
  предполагаемую запись, `write` — запись вне двух каталогов. В режиме `full`
  вызова Jev нет и путь не ограничен. Соответствие задаче и сетевые эффекты Jev
  не проверяет. Все переменные окружения передаются shell, поэтому не отправляй
  секреты в текст команды. Jev не является границей безопасности
  ОС: скрытые побочные эффекты, кеши и дочерние процессы могут выйти за
  оценённые намерения.
- Отмена и таймаут завершают управляемую группу процессов через SIGTERM,
  затем SIGKILL. Не обещай завершение потомков, отделившихся от группы.
- У Horizon нет встроенной песочницы: workspace задаёт начальный каталог,
  команды работают с правами пользователя ОС, внешние эффекты не
  откатываются. Учитывай это при тестировании файловых и shell-операций.

## Границы изменений

Перед работой проверяй ветку и рабочее дерево, сохраняй чужие незавершённые
изменения. Ограничивай diff задачей; не добавляй новые зависимости, абстракции
или миграции без необходимости. При изменении пользовательского поведения
обновляй соответствующую документацию. В отчёте указывай результат, фактически
выполненные проверки и оставшиеся ограничения.
