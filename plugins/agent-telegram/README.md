# Входной адаптер Telegram

`agent-telegram` получает обновления Telegram long polling. Он сохраняет
ожидающее сообщение и подтверждает offset после долговечной записи daemon.
Уточнения попадают в текущий ход на ближайшей безопасной границе или в следующий
ход того же диалога. Для каждого чата daemon использует свою привязку workspace
и сессии. Миграция группы в супергруппу сохраняет эту привязку.

Установите `agent`, `telegram` и `agent:telegram` через
`horizon manager plugins install <имя>`. При первой установке manager включает
расширение и input; токен и владельца заполните в `config.yaml`:

```yaml
extensions:
  telegram:
    enabled: true
    communication: true
plugins:
  telegram:
    bot_token: ""
    owner_user_id: 0
  agent:
    adapters: [telegram]
    max_active_adapter_dialogs: 2
  agent-telegram:
    private_access: write
    group_access: read
    group_defaults:
      owner_only: true
      response_mode: mention
    groups: {}
    history_messages: 20
    idle_compact_after: 12h
```

Заполните параметры бота и запустите `horizon agent start`. Адаптер
перечитывает свои настройки после перезапуска. `workspace_dir` по умолчанию
равен `<home>/workspaces/telegram`; явно заданный относительный путь
разрешается от `<home>`.

Личные сообщения принимаются только от владельца. Настройки отдельной группы
задаются в `groups` по отрицательному ID, который показывает
`horizon telegram list`. `owner_only` ограничивает инициаторов хода. Текст
остальных участников может попасть в ограниченный контекст этого же чата.

В `mention` триггером служит явное упоминание `@username` бота. В
`conversation` каждое подходящее текстовое сообщение входит в новый или
активный ход. Учитывайте расход модели при большом потоке таких сообщений.
Доступ бота к групповым сообщениям зависит от его настроек Telegram.

Модель сама решает, отправить сообщение, несколько сообщений или промолчать.
Молчание допустимо и при упоминании. Итог хода и диагностика остаются в
Horizon. Пока ход активен, Telegram может показывать typing. После простоя
daemon может сжать достаточно большой checkpoint, а новый вход отложит или
отменит обслуживание. Значение `idle_compact_after: 0s` выключает его.

Адаптер сохраняет диагностическое сообщение последней ошибки в
`<home>/gateway/telegram-adapter.error`. Подтверждённые внешние отправки и
миграция прежней установки описаны в [README расширения](../telegram/README.md).

## Документы и фотографии

Адаптер принимает `document` и `photo`, в том числе без текста. Для медиа
используются caption и caption_entities: упоминание бота в подписи работает
как упоминание в обычном сообщении. Правила owner/private/group сохраняются;
вложения сообщений, не запускающих ход, не скачиваются. Их метаданные могут
попасть в недавнюю историю, но локальный путь не обещается. В цитате доступны
только уже подготовленные вложения известного сообщения.

Перед submit адаптер сохраняет файл в
`<workspace>/attachments/<chat-origin>/<message-id>/<generated-name>`.
Имя на диске генерируется из идентификаторов, исходное имя остаётся в метаданных.
Каталоги имеют права `0700`, файлы `0600`; существующие пользовательские файлы
не перезаписываются. У фотографии выбирается самый большой доступный вариант.
Изображение, присланное документом, остаётся документом и сохраняет байты.
Миграция группы сохраняет её исходный Origin и workspace.

В сообщение Horizon добавляются текст/подпись и массив `attachments`: kind,
name, mime_type (как заявил отправитель), size, sha256, state и абсолютный path
только для `ready`. Файл уже существует к моменту передачи входа в daemon.
Если скачивание не удалось, модель получает `failed` с причиной без ложного пути,
а подпись сохраняется. Имена и содержимое вложений являются данными, не командами.

Предел загрузки — 20 000 000 байт, в том числе при неизвестном file_size;
HTTP-таймаут — 40 секунд, полный бюджет попытки подготовки — 45 секунд.
Счётчик сохраняется до I/O; после трёх неудачных попыток вложение получает failed.
Постоянный отказ API или превышение размера завершают подготовку сразу.
После перезапуска адаптер проверяет checksum готового файла или восстанавливает
незавершённую загрузку. Подменённый файл отмечается ошибкой, не затирается.
После сохранения итогового payload повтор submit использует тот же operation ID
и неизменный текст, включая пути; изменение файла позднее не переписывает
уже принятую историю. Пользовательские файлы не удаляются после хода.

Альбом поступает отдельными сообщениями с общим media_group_id; адаптер не ждёт
его завершения. Отдельного распознавания изображений, OCR, распаковки и конвертации
нет. **Локальный путь к изображению не передаёт его пиксели модели.** Визуальный
анализ требует отдельной возможности ядра. Формат Bot API:
[Message](https://core.telegram.org/bots/api#message),
[getFile](https://core.telegram.org/bots/api#getfile).
