# Отправка сообщений в Telegram

`horizon-telegram` подключает `telegram__send_message`, `telegram__send_file` и `telegram__read_send`
к агенту. Хост выбирает чат входящего хода. Автономный ход, включая задачу
таймера, может писать в личку владельца. Бот должен иметь доступ к выбранному
чату. Для лички владелец сначала открывает диалог с ботом в Telegram.

Установите расширение командой `horizon manager plugins install telegram`.
В `config.yaml` заполните `plugins.telegram.bot_token` и
`plugins.telegram.owner_user_id`. Храните токен в приватном файле конфигурации.
Manager при первой установке добавляет `extensions.telegram.enabled: true`
и `extensions.telegram.communication: true`. Для отключения инструментов
выставьте `enabled: false`, для запрета отправки — `communication: false`.
Разрешение коммуникации действует в `read`, `write` и `full`. Файловые
ограничения хода сохраняются. Для входящих сообщений установите также
[адаптер](../agent-telegram/README.md).

`send_message` принимает `text` и разбивает длинный текст на части. Успешная
доставка возвращает `state: confirmed`, ID чата и ID всех отправленных
сообщений. `unknown` означает, что Telegram мог принять часть до потери
ответа. Сверьте результат через `telegram__read_send` или
`horizon telegram read --operation-id ID`. По частям видны подтверждённые
ID и состояния `confirmed`, `rejected`, `pending`, `unknown`. Восстанавливайте
неизвестный результат по истории Telegram. Новый вызов с тем же текстом
может его продублировать.

## Проверка без модели

```sh
horizon telegram check
horizon telegram send 'hi!'
horizon telegram list --json
horizon telegram read --operation-id ID
```

`check` проверяет настройки, личность бота через `getMe` и отсутствие webhook,
мешающего polling. Сообщения не отправляет и доступность лички владельца не
подтверждает. `send TEXT` отправляет одно тестовое сообщение в личку
`owner_user_id`; владелец должен предварительно открыть диалог с ботом.
Текст — от 1 до 4096 символов. Эти команды не обращаются к модели и не требуют
включения расширения или коммуникации в `extensions.telegram`. При вызове
из хода диагностическая отправка разрешена только в `full`.

Тестовая отправка печатает ID сообщения, не создаёт запись в журнале
`telegram__send_message` и не повторяет запрос автоматически. При неизвестном
исходе проверьте историю Telegram перед повтором. `list` показывает
зарегистрированные чаты, JSON имеет `schema_version: 2`. `read` читает журнал
отправок расширения. Параметры каждой команды доступны через `--help`.

## Миграция прежнего Telegram

1. Остановите прежнюю службу и отключите её автозапуск штатным менеджером ОС.
   Остановите `horizon agent`, если он запущен. Обновите Horizon и установите
   `agent`, `telegram` и `agent:telegram` через manager. Установка добавляет
   недостающие шаблоны, сохраняя старые поля.
2. Запустите `horizon telegram migrate --check`. Команда проверяет установленные
   бинарники, настройки, старые привязки и блокировки без запросов к Telegram или
   провайдеру модели. Для старой службы проверяются локальная регистрация и
   постоянная блокировка polling.
3. Выполните `horizon telegram migrate --apply`. Копии конфигурации, состояния
   gateway и существующей очереди daemon хранятся в
   `<home>/gateway/telegram-migration-v2/`. Привязки существующих сессий
   переносятся без редактирования их истории. Ожидающие входящие сообщения
   получают устойчивые ID операций. Старые задания с неизвестным исходом
   блокируют последующие ходы в том же диалоге до проверки оператором.
   Прежние `generated`, `sending` и `unknown` можно разобрать в сохранённом
   `legacy-state.yaml`; автоматической доставки этих результатов больше нет.
   Повторный `--apply` завершает прерванный перенос. Старый лимит параллельных
   чатов переносится в `max_active_adapter_dialogs`, если он ещё не задан.
4. Установите файл службы через `horizon agent service install` и запустите
   `horizon agent start`. Миграция сама службы и shell-файлы не меняет.

До первого запуска polling или явной отправки можно остановить daemon и
выполнить `horizon telegram migrate --rollback`. Команда восстанавливает
резервные копии, если файлы миграции совпадают с ожидаемым состоянием. Для
прерванного отката повторите `--rollback`. После запуска новой обработки
сверьте действия в Telegram, очередь daemon и резервные копии вручную.
Восстановление старой очереди после внешней доставки может повторить отправку.

## Отправка файлов моделью

Расширение предоставляет `telegram__send_file`:

```json
{"path":"reports/result.pdf","caption":"Готовый отчёт","as_photo":false}
```

Все три аргумента обязательны; для отсутствующей подписи передайте пустую строку.
`as_photo: false` отправляет исходные байты документом. `true` отправляет
JPEG/PNG как фотографию; Telegram может обработать изображение. Другие форматы
передавайте документом, автоматической конвертации нет.

Относительный path разрешается от workspace текущего хода; абсолютный допустим
только внутри него. Symlink наружу, каталоги и специальные файлы запрещены.
Для файла вне workspace сначала явно подготовьте копию внутри. Проверка и
чтение используют привязанный к workspace файловый дескриптор, чтобы подмена
symlink не позволяла выйти за его границы. Это ограничение send_file, а не
общая песочница Horizon.

Получателя определяет host route; chat_id нельзя передавать инструменту.
Без маршрута используется личка владельца. Требуется то же отдельное разрешение
`extensions.telegram.communication`, что и для send_message. Файловый режим
`read` сам по себе не запрещает явно разрешённую коммуникацию.

Перед отправкой создаётся приватный снимок в outbox (`.file-*`, права `0400`),
затем фиксируется операция с размером и SHA-256. Повтор того же operation_id
использует зарегистрированный снимок, даже если исходник изменён или удалён.
Изменённые аргументы или попытка заменить текстовую операцию файловой отклоняются.
Новый файл по тому же пути — новая операция только после явного решения агента;
не используйте это для повтора доставки с неизвестным исходом.

Результат сохраняет state, operation_id и message_ids; для файла добавляются
kind и file (исходный path, name, size, sha256, as_photo). `telegram__read_send`
читает как старые текстовые, так и файловые операции. `confirmed` означает
подтверждённый message ID; `unknown` после обрыва или ошибки сохранения требует
проверки журнала и истории Telegram. Автоматического повторного POST нет.
Подтверждённая исходящая история содержит метаданные вложения, не бинарные данные.
Снимки и журналы сохраняются после хода; автоматическая очистка не добавлена.

Консервативные пределы облачного Bot API, проверенные 14 ноября 2026:
документ — 50 000 000 байт, фотография — 10 000 000 байт; пустой файл запрещён.
Подпись — до 1024 Unicode-символов без parse_mode. Для фото сумма ширины и высоты
не больше 10000, отношение большей стороны к меньшей не больше 20.
Источник: [sendDocument](https://core.telegram.org/bots/api#senddocument),
[sendPhoto](https://core.telegram.org/bots/api#sendphoto).

При обновлении остановите supervisor, обновите ядро и оба плагина из одной
ревизии, затем запустите его снова. Старые текстовые записи читаются без миграции.
Возврат к версии без файловой поддержки после появления файлового outbox не
поддерживается: старый код не умеет интерпретировать эти операции.
