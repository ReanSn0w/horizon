# Horizon Manager

Самостоятельный `horizon-manager` устанавливает Horizon из исходников и управляет
плагинами официального репозитория `ReanSn0w/horizon`. Нужны Git и установленный
Go не ниже версии `go.mod` выбранной ревизии. Менеджер использует
`GOTOOLCHAIN=local`: другой Go автоматически не скачивается. Go может скачивать
зависимости проекта. Поддерживаются macOS/Linux, amd64/arm64.

## Первая установка

Скачиваемый bootstrap-бинарник — только `horizon-manager`.
[Релизы](https://github.com/ReanSn0w/horizon/releases/latest) содержат:

| Система | Процессор | Бинарник |
| --- | --- | --- |
| Linux | x86_64 | `horizon-manager-linux-amd64` |
| Linux | aarch64 | `horizon-manager-linux-arm64` |
| macOS | Intel | `horizon-manager-darwin-amd64` |
| macOS | Apple Silicon | `horizon-manager-darwin-arm64` |

Скачайте бинарник и `SHA256SUMS` из одного релиза. Сравните строку для выбранного
файла с `sha256sum <файл>` (Linux) или `shasum -a 256 <файл>` (macOS), затем:

```sh
chmod +x ./horizon-manager-darwin-arm64
./horizon-manager-darwin-arm64 install
```

В примере выбран Apple Silicon; для другой платформы используйте имя из таблицы. На macOS сборки не имеют Developer ID/notarization.
Установка по умолчанию выбирает последний стабильный release. Для ручной сборки:

```sh
go build -o /tmp/horizon-manager ./plugins/manager
/tmp/horizon-manager install
```

Интерактивная установка предлагает `HORIZON_HOME` или `~/.horizon` и позволяет
ввести другой путь. `--home` имеет приоритет. В скриптах требуется `--yes`:

```sh
/tmp/horizon-manager install --home "$HOME/.horizon" --branch master --yes --shell zsh
```

Менеджер создаёт `bin`, `source`, `dialogs`, `memory/workspaces`, стартовые навыки,
`config.yaml`, `AGENTS.md` и `.manager`. Собирает ядро и себя, затем печатает
выбранный источник, commit и подсказку по настройке моделей. Agent и Browser
не устанавливаются автоматически. `SOUL.md` остаётся пользовательским файлом.
Повторный `install` восстанавливает отсутствующие ресурсы, пересобирает управляемый
набор из выбранного источника и сохраняет существующие настройки, сессии и навыки.

Менеджер **не открывает и не изменяет shell-конфигурацию**. В конце он только
показывает команды `HORIZON_HOME` и `PATH`: их можно исполнить в текущем терминале
и самостоятельно добавить в startup-файл. Формат выбирается по `SHELL` или
`--shell bash|zsh|fish`, при неизвестном shell используется zsh.
Родительское окружение не меняется. Например для zsh:

```sh
export HORIZON_HOME="$HOME/.horizon"
export PATH="$HORIZON_HOME/bin:$PATH"
```

После этого заполните провайдеров и профили моделей в `config.yaml` согласно
[основному README](../../README.md). Установка и обновление не требуют API-ключей.

## Источник и обновление

Источник хранится отдельно от фактически установленной ревизии:

```yaml
installation:
  source:
    type: branch
    branch: master
```

Для последнего стабильного опубликованного GitHub release:

```yaml
installation:
  source:
    type: release
```

Без явного источника новая установка выбирает `release`. Draft/prerelease не
используются; отсутствие release, лимит API или несовместимая структура старого
тега дают ошибку. Автоматического перехода на ветку нет. Ветка `release` задаётся
однозначно как `type: branch` и `branch: release`.

```sh
horizon manager update
horizon --home /another/home manager update
# Прямой вызов работает и при неисправном основном бинарнике:
/path/to/home/bin/horizon-manager update --home /path/to/home
```

`update` перечитывает источник, фиксирует один commit и собирает ядро, менеджер
и только управляемые установленные плагины. Локальные изменения в `source`,
включая ignored/untracked-файлы, неожиданный origin и ручная смена HEAD запрещают
замену. Сохраните собственные изменения вне checkout перед обновлением.
Не храните пользовательские файлы в `source`: чистый checkout заменяется целиком.

## Актуализация конфигурации

`install` (включая повторный) и `update` обновляют конфигурацию вместе с бинарниками:

- При первом создании `config.yaml` используется `config.example.yaml` из
  **выбранного commit**, а не встроенный шаблон запущенного bootstrap-менеджера.
- В существующий файл добавляются недостающие основные параметры и вложенные
  настройки. Уже заданные значения, включая `false`, `0`, пустые строки и списки,
  сохраняются. Комментарии остаются; YAML может изменить форматирование отступов.
- Карты `models` и `providers` принадлежат пользователю. Менеджер не добавляет
  туда примерные профили и подключения. Отсутствующие `default_model` и
  `decision_model` дополняются из шаблона лишь при наличии соответствующего
  профиля. Ключи API и выбор новых моделей заполняются пользователем.
- Если секции `memory` не было, она добавляется выключенной. Недостающий
  `memory.model` следует пользовательскому `default_model`. Уже заданная модель
  и состояние памяти не меняются. Расширения сами не включаются.
- Настройки управляемых плагинов дополняются по шаблонам собранных бинарников.
  Примеры из общей секции `plugins` не накладываются на существующие настройки.
- Известные миграции выполняются явно: устаревшая память переносится из плагина
  в ядро, настройки `daemon` переименовываются в `agent`, `mode: unit` удаляется,
  если его больше нет в шаблоне выбранной версии. Для старой ревизии с `mode`
  поле сохраняется или восстанавливается. Неизвестные поля не удаляются.

Конфигурация подготавливается в staging и попадает в ту же транзакцию, что и
бинарники. При ошибке применяется rollback. Ссылка `config.yaml` и права её цели
сохраняются. Если актуализация ничего не изменила, файл не перезаписывается;
менеджер сообщает `Configuration already up to date`.

Новый неизвестный текущему менеджеру формат шаблона вызывает понятную ошибку
до замены установленного набора: используйте manager из выбранной ревизии.
Повреждённый YAML, конфликт старой и новой секций, неподдерживаемое значение
старого поля требуют явного исправления. Это не повод угадывать значения или
терять пользовательские настройки. Отдельная настройка моделей не требуется
для самой установки: пустые стартовые поля остаются для последующего заполнения.

## Плагины

```sh
horizon manager plugins list
horizon manager plugins install browser
horizon manager plugins install telegram
horizon manager plugins remove browser
```

`list` отдельно показывает доступность в checkout (`AVAILABLE`), управление
менеджером (`MANAGED`) и включение в `agent_plugins` (`ENABLED`). Менеджер обязателен
и не удаляется этой командой. Описания `plugins/*/plugin.json` задают имя команды,
Go-пакет и имя бинарника без произвольных shell-команд. `plugins/agent` соответствует
`agent` и `horizon-agent`; `plugins/telegram` — `telegram` и `horizon-telegram`.

`plugins install` собирает только выбранный плагин из **установленного commit**,
без fetch и скрытого обновления ядра. Шаблон настроек добавляет недостающие поля,
сохраняя существующие значения. Повторная установка пересобирает плагин и дополняет
шаблон. `agent_plugins` и службы автоматически не включаются.

`plugins remove` удаляет только управляемый бинарник и исключает имя из
`agent_plugins`; настройки и данные сохраняются. Посторонние файлы в `bin`
не присваиваются менеджером и не перезаписываются. Если установленный плагин
пропал из новой ревизии, обновление останавливается до замены: удалите плагин
явно или выберите совместимый источник.

## Обслуживание и восстановление

Изменяющие операции сериализуются `.manager/operation.lock`. Рабочие команды
ядра и официальных плагинов удерживают совместную `.manager/maintenance.lock`,
менеджер — исключительную. При активном ходе или службе операция завершается
ошибкой: завершите ходы, остановите службы и повторите её. Менеджер не убивает
чужие процессы. Для прежних версий дополнительно проверяются блокировки сессий
и Telegram. Сторонние бинарники, которые не соблюдают протокол блокировки,
нужно остановить самостоятельно.

Сборка и проверка метаданных завершаются до замены рабочих файлов. Применение
набора не является одной атомарной операцией: `.manager/transaction` содержит
журнал и резервные копии. Ошибка откатывает набор; после аварийного прерывания
следующая изменяющая команда восстанавливает прежнее состояние перед новой
попыткой. Config symlink сохраняется, обновляется его разрешённая цель.
Состояние `.manager/state.json` записывается последним.

Сохраните исходный скачанный менеджер вне home. При повреждении установленного
менеджера используйте его с явным `--home`. Не удаляйте `.manager/transaction`
вручную до восстановления. Если recovery сообщает об изменившемся symlink
конфига, верните его прежнюю цель. При ошибке восстановления менеджер сохраняет
резервные копии и сообщает о необходимости вмешательства. `plugins list`
при незавершённой транзакции предлагает сначала выполнить восстановление.

## Переход со старой установки

Старый `<home>/plugins` больше не сканируется Horizon. Выберите перенос известных
плагинов явно:

```sh
/tmp/horizon-manager install --home "$HOME/.horizon" --branch master --adopt telegram --adopt browser
```

Перенос означает сборку выбранных плагинов в `bin`; старые файлы и неизвестные
плагины остаются на месте. Коллизия с неуправляемым бинарником в `bin` требует
явно переместить его перед установкой. Основной `horizon` вне home не удаляется:
менеджер сообщает о нём, если находит его в PATH. Проверьте порядок PATH.

Перед переносом Telegram остановите прежнюю службу. После установки удалите
старое определение службы и установите его снова из нового бинарника; менеджер
не переписывает launchd/systemd-конфигурацию. Подробности — в
[README Agent](../agent/README.md). Данные `<home>/gateway` сохраняются.

## Ручная сборка bootstrap-артефактов

Из чистого checkout выбранного commit на машине сопровождающего:

```sh
mkdir -p /tmp/horizon-manager-artifacts
for target in darwin/amd64 darwin/arm64 linux/amd64 linux/arm64; do
  os=${target%/*}
  arch=${target#*/}
  CGO_ENABLED=0 GOTOOLCHAIN=local GOOS="$os" GOARCH="$arch" \
    go build -trimpath -o "/tmp/horizon-manager-artifacts/horizon-manager-$os-$arch" ./plugins/manager
done
```

Эта команда создаёт файлы, но не публикует их. Makefile предназначен для разработки:
`make build-manager`, `make install`, `make install-plugins PLUGINS=browser`.
Ручная установка Makefile не регистрирует бинарники в состоянии менеджера.

## Pipeline и выпуск релиза

[manager-release.yml](../../.github/workflows/manager-release.yml) проверяет изменения
в `master`, ветке текущих доработок и pull request в `master`. Матрица использует
нативные runners Linux/macOS на amd64/arm64: выполняет `go test -race ./...`,
`go vet ./...`, собирает manager без CGO, проверяет справку и версию метаданных.
Версия берётся из тега, commit встраивается в бинарник. Windows не собирается.

Для нового релиза добавьте `docs/releases/vX.Y.Z.md` и отправьте тег `vX.Y.Z`
на проверенный commit. После успеха всех четырёх jobs отдельный job с
`contents: write` формирует `SHA256SUMS`, загружает полный набор в draft release
и только затем публикует его. Повторный запуск может завершить draft, но не
перезаписывает уже опубликованный релиз. `workflow_dispatch` выполняет проверку
и сборку без публикации. Используются официальные Actions, закреплённые по SHA;
личный токен для выпуска не нужен.
