## Что мы делаем?

Добавляем в цикл агента проверяемый предел роста рабочего контекста. Horizon
сохраняет автоматическое сжатие Responses API, но не продолжает десятки
дорогих запросов, если провайдер не вернул элемент `compaction` после
достижения порога. Защита действует и внутри долгого хода с инструментами, и
при возобновлении крупной сессии. Состояние инструментов с неизвестным
результатом не теряется и не выполняется повторно.

## Для чего мы делаем?

В наблюдаемой сессии `compact_threshold` равен 200 000, записанных сжатий
нет, а один запрос через OpenRouter содержал 495 179 входных токенов.
Повторная передача такого контекста в ходе с инструментами привела к
значительному расходу. Пока неизвестно, где именно не срабатывает
автоматическое сжатие; размер JSON-файла сессии нельзя считать числом
оплачиваемых токенов.

## План

- [ ] Уточнить контракт сжатия на используемом маршруте Responses API.
  - [ ] На отдельной тестовой сессии с тем же провайдером проверить, принимает
    ли `/responses` `context_management` и возвращает ли элемент `compaction`
    при пороге ниже фактического контекста.
  - [ ] Отдельно проверить `/responses/compact` на тестовой сессии и
    зафиксировать ответ при неподдерживаемом endpoint без изменения живой
    Telegram-сессии.
  - [ ] Сопоставить отправленный порог, числовой `usage` и возвращённые API
    items; определить, какой механизм доступен для защитного сжатия.

- [ ] Ввести решение о сжатии между запросами модели в `internal/agent`.
  - [ ] После каждого успешного ответа разбирать `usage.input_tokens` и
    наличие нового элемента `compaction`; не принимать байтовый размер JSON
    за точное число токенов.
  - [ ] Перед следующим запросом при превышении настроенного порога и
    отсутствии автоматического сжатия вызывать поддерживаемый механизм
    явного сжатия под существующей блокировкой сессии.
  - [ ] Для первого запроса нового хода использовать сохранённую оценку
    предыдущего рабочего окна; для старых сессий без неё предусмотреть
    консервативный путь, явно обозначив неточность оценки.
  - [ ] После явного сжатия заменить только рабочее окно, сохранить полный
    журнал и непрозрачные API items в совместимом формате сессии.
  - [ ] Если сжатие недоступно или завершилось ошибкой, остановить дальнейший
    рост расхода с адресной ошибкой и сохранённой историей вместо повторного
    запуска инструментов.

- [ ] Ограничить совокупный расход длинного хода.
  - [ ] Добавить настраиваемый лимит входных токенов за ход по фактическому
    `usage`, оставив существующий `max_model_requests` как отдельный лимит.
  - [ ] Проверять лимит перед очередным запросом; при отсутствии числового
    `usage` явно сообщать, что точный токенный предел не подтверждён.
  - [ ] Установить безопасные значения в обоих шаблонах конфигурации и
    сохранить совместимость старого `config.yaml` без перезаписи при `init`.

- [ ] Проверить сохранность сессии и последствия инструментов.
  - [ ] В `internal/agent/runtime_test.go` покрыть рост контекста без
    автоматического сжатия, успешное явное сжатие, отказ endpoint и достижение
    лимита токенов.
  - [ ] Проверить сжатие после `function_call_output`, ожидание управляемого
    shell-процесса, прерывание и восстановление без слепого повтора команды.
  - [ ] Проверить чтение прежних сессий без новой метрики и соответствие
    сериализации `internal/session`.

- [ ] Обновить описание и выполнить проверки.
  - [ ] Обновить `README.md`, `docs/TELEGRAM_LATENCY.md` и оба шаблона
    конфигурации с точным различием между порогом провайдера и локальной
    защитой Horizon.
  - [ ] Выполнить `gofmt`, `go build -o /tmp/horizon-dev .`, `go test ./...`,

  - [ ] На отдельной тестовой сессии сравнить токены и стоимость хода до и
    после изменения; не заявлять экономию по mock-тестам.
