## Что мы делаем?

Создаём плагин `plugins/manager`, собираемый в самостоятельный бинарник
`horizon-manager`. Пользователь скачивает только менеджер и запускает
`./horizon-manager install`. После установки те же операции доступны как
`horizon manager <команда>`. Режим определяется явной командой, а не местом
расположения бинарника. Прямой запуск менеджера сохраняется для восстановления
установки, когда основной Horizon не запускается.

Все бинарники размещаются в `<home>/bin`, checkout исходников — в `<home>/source`.
Менеджер готовит home, собирает Horizon и выбранные плагины установленным Go,
обновляет исходники и установленный набор, управляет плагинами нашего репозитория.
Пользователю нужны Go и Git; `make` не требуется для работы менеджера.

Предлагаемый интерфейс:

```sh
./horizon-manager install
./horizon-manager install --home /path/to/home --branch codex/repository-refactoring
horizon manager update
horizon manager plugins list
horizon manager plugins install browser
horizon manager plugins remove browser
```

Источник выбирается в `config.yaml` отдельно от провайдеров моделей:

```yaml
installation:
  source:
    type: release
```

Либо:

```yaml
installation:
  source:
    type: branch
    branch: codex/repository-refactoring
```

`release` — последний опубликованный стабильный релиз официального репозитория,
не draft и не prerelease. Собираются исходники его тега, не скачиваются готовые
Horizon и плагины. `branch` — конкретная ветка того же репозитория. Тип и имя
разделены, поэтому ветку с именем `release` тоже можно выбрать однозначно.
Репозиторий пока фиксирован: `ReanSn0w/horizon`; сторонние источники вне задачи.
По умолчанию новая установка использует `release`. При отсутствии релиза или
несовместимости его исходников менеджер сообщает ошибку, без перехода на ветку.
Первую проверку новой схемы проводим с явно указанной рабочей веткой.

Менеджер всегда устанавливается вместе с Horizon. Agent и Browser остаются
необязательными. Источник, выбранный при установке, сохраняется в конфигурации;
`update` перечитывает его. Обновляются Horizon, сам менеджер и только плагины,
которыми менеджер уже управляет. Список в `agent_plugins` по-прежнему отвечает
за включение инструментов и не заменяет перечень установленных бинарников.

Это план реализации, а не восстановление прежней системы distribution.
Автоматизация релизов, workflow, отдельный каталог удалённых пакетов, сторонние
репозитории плагинов и автоматическое обновление по расписанию сюда не входят.
Публикация релиза и изменения master не входят в работу. По процессу выполнения
плана рабочая ветка объединяется только с исходной `codex/repository-refactoring`.

## Для чего мы делаем?

Сейчас `internal/bootstrap` и `horizon init` создают home, Makefile устанавливает
Horizon в `BIN_DIR`, а плагины — в `<home>/plugins`. Установка и обслуживание
разделены между несколькими механизмами. Новый процесс получает одного владельца:
менеджер управляет исходниками, бинарниками, начальными ресурсами и составом
установки. Основной CLI выполняет агентские задачи и делегирует команду `manager`
по существующему протоколу внешних команд.

## Результат проверки

- `go test ./...`, `go vet ./...`, `go test -race ./...` — успешно.
- Полная локальная установка из Git: ядро, manager, Browser, Telegram; повторная установка, update и remove без обращения к внешним API.
- Проверены release/branch, смена источника, движение ветки при сборке, несовместимый Go, отмена, dirty/foreign checkout, активные блокировки, ошибки прав, rollback каждой замены и восстановление прерванной транзакции.
- Проверены комментарии и symlink конфигурации, неуправляемые файлы, сохранение данных и печатные shell-команды.
- Bootstrap собран для darwin/amd64, darwin/arm64, linux/amd64 и linux/arm64. Выполнение тестов — macOS arm64; запуск на остальных платформах не проверялся.
- Go в PATH был 1.26.5; финальные проверки и bootstrap-сборки выполнены явным установленным Go 1.26.7 с GOTOOLCHAIN=local.
- Релизы и bootstrap-артефакты не публиковались. Личный home и shell-конфигурация не изменялись.
