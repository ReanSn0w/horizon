## Что мы делаем?

Добавляем подключаемые команды по модели внешних исполняемых файлов:
`horizon <имя> <аргументы>` запускает `<home>/plugins/horizon-<имя>`.
Установленные плагины принадлежат выбранному Home Horizon: явный `--home`
имеет приоритет над `HORIZON_HOME`, по умолчанию используется `~/.horizon`.

Исходники разрабатываемых в этом репозитории плагинов хранятся в корневой
директории `plugins/`, каждый плагин — в `plugins/<имя>/`. Это дерево исходников,
а `<home>/plugins/` — каталог установленных исполняемых файлов. Horizon
не обнаруживает и не запускает плагины из репозитория автоматически.

Используем Go и существующий `go-flags` для CLI Horizon. Плагин является
отдельным процессом; его язык и парсер аргументов не ограничиваются Go.
Метаданные получаем служебной командой, без отдельного манифеста. Ниже
зафиксирован предлагаемый контракт первой версии для реализации.

В объём входят обнаружение, справка, запуск, подготовка каталога при `init`,
минимальный пример плагина и документация. Менеджер скачивания и обновлений,
реестр пакетов, поиск через PATH, хуки агента, новые инструменты модели,
автоматическая установка навыков и публичный Go SDK в эту задачу не входят.
Сам `AGENTS.md` обновляется при реализации плана, а не при его составлении.

## Для чего мы делаем?

Сейчас команды регистрируются в `internal/cli`, и добавление новой команды
требует изменения основного бинарника. Отдельные исполняемые плагины позволят
поставлять дополнительные команды независимо от Horizon, сохранив привычный
CLI и изоляцию наборов расширений между разными home.

Процессная граница не является песочницей: плагины работают с правами
пользователя ОС. Они не получают поддерживаемого интерфейса для прямой записи
в хранилище сессий. Агент сможет вызывать установленные команды через
существующий `shell_exec`; каталог плагинов сам по себе не добавляется
в инструкции модели.

## План

- [ ] Зафиксировать протокол подключаемых команд в новом `docs/PLUGINS.md`.
  - [ ] Описать единственный каталог обнаружения `<home>/plugins/` и правило имени файла `horizon-<имя>`, где имя соответствует `[a-z][a-z0-9-]*`.
  - [ ] Зарезервировать имена встроенных команд и их алиасов; конфликтующий плагин не может подменить встроенную команду или её подкоманду.
  - [ ] Описать служебный вызов `horizon-<имя> horizon-plugin-metadata`: stdin закрыт, stdout содержит ровно один JSON-объект с обязательными `protocol_version: 1`, непустыми `version` и `description`; неизвестные дополнительные поля допустимы.
  - [ ] Установить для получения метаданных таймаут 2 секунды и пределы stdout/stderr по 64 КиБ; ошибка процесса, превышение лимита, лишние данные или неподдерживаемая версия делают плагин недоступным для запуска.
  - [ ] Описать обычный запуск: имя команды удаляется из argv, остальные аргументы передаются буквально; плагин сам обрабатывает свои подкоманды, `--help` и `--`.
  - [ ] Описать окружение: наследовать окружение процесса, переопределять `HORIZON_HOME` разрешённым home и `HORIZON_EXECUTABLE` абсолютным путём к запущенному Horizon; глобальный `--verbose` относится к диагностике Horizon и не добавляется в argv плагина.
  - [ ] Зафиксировать коды завершения: обычный exit code плагина передаётся без изменения; отмена через Ctrl+C даёт 130, прочие сигналы — `128 + номер сигнала`; ошибки запуска Horizon дают 1, ошибки аргументов или несовместимости протокола — 2. Коды встроенных команд сохраняются.
  - [ ] Уточнить инициализацию: обычный вызов плагина требует существующего `config.yaml`, но не загружает настройки провайдера; корневая справка и `horizon <плагин> --help` не требуют инициализированного home и ничего в нём не создают силами Horizon.

  - [ ] Перечислять только непосредственные исполняемые файлы с нужным префиксом; поддержать symlink на исполняемый файл, отклонять каталоги, специальные файлы и невалидные имена.
  - [ ] Считать отсутствующий каталог пустым набором; различать отсутствие, ошибку чтения каталога и неисправность отдельного кандидата.
