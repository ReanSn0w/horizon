## Что мы делаем?

Подключаем отдельную обязательную модель решений Jev для ходов агента и
оцениваем ею каждый вызов `shell_exec` до запуска команды. Диалоговая модель
продолжает работать через существующий Responses API; Jev получает собственные
URL, ключ и ID модели, поскольку провайдеры могут различаться. Для Jev через
OpenRouter используем [`POST /api/alpha/decisions`](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request)
с `state`, типизированными `questions` и моделью `typesafe/jev-1.13`.
[Документация Jev](https://openrouter.ai/docs/guides/community/jev) описывает
формат вероятностных ответов, а [пример проверки вызовов инструментов](https://openrouter.ai/docs/cookbook/building-agents/gate-tool-calls-with-jev)
показывает, как принимать решение в коде.

Для каждого запуска пользователь выбирает режим оценки команд:

- `read` — допускать команды, которые читают файлы, но не должны изменять их;
- `write` — допускать команды, чьи предполагаемые изменения файлов находятся
  в пределах текущего рабочего каталога или выбранного `HORIZON_HOME`;
- `full` — допускать операции с файловой системой без ограничения по пути,
  сохраняя проверку соответствия поручению пользователя.

Пользователь передаёт режим как `horizon resume --access read|write|full`.
Если в обычном запуске `resume` флаг опущен, действует `write` по умолчанию.
Вложенным экземплярам Horizon `shell_exec` передаёт эффективный режим через
служебную переменную `HORIZON_INHERITED_ACCESS`. Она относится ко всему
дочернему процессу Horizon и имеет приоритет над `resume --access`: если она
задана, значение флага `resume` игнорируется при любом конфликте. При
отсутствии переменной Horizon считает запуск самостоятельным; пользователь не
должен её задавать.
Рабочий каталог и выбранный home фиксируются при запуске. Все три режима — правила
для оценки Jev, а не изоляция ОС: команда запускается с нынешними правами
пользователя, всеми переменными окружения и доступом к сети. Jev видит текст
команды и переданный контекст, но не может гарантировать её фактические
побочные эффекты. При отказе или неопределённости команда не исполняется,
модель получает понятный результат и может предложить другой вызов; отдельного
запроса подтверждения пользователю нет.

После подключения проверки убираем отдельные файловые инструменты
`file_create`, `file_read`, `file_update`, `dir_list`, `dir_delete`. Остаются
`shell_exec` и `skill_read`; встроенный навык работы с файлами объясняет
модели практические команды. Навык не является механизмом контроля доступа.

## Для чего мы делаем?

Сейчас `internal/agenttool/shell_unix.go` запускает `/bin/sh` с правами
пользователя, а отдельные файловые инструменты в `internal/agenttool` обходят
общую точку оценки команд. Отдельный провайдер решений позволит быстро
проверять уместность вызова в выбранном режиме и упростить набор инструментов,
не спрашивая пользователя перед каждой командой. При этом названия режимов не
должны создавать ложного обещания песочницы: скрипт, вложенный процесс или
неявная запись могут сделать больше, чем следует из текста команды.
