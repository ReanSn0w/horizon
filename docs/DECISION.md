# Decision

`horizon decision request.json` или `horizon decision - -o result.json`
принимает один путь к UTF-8 JSON-файлу; `-` читает stdin. Флаг `-o`
допускается до или после пути. Команда встроена в Horizon.

Вход — объект `{state, questions}` без других верхнеуровневых полей.
Каждый вопрос имеет непустое имя и поле `instructions`. Ответ на каждый
вопрос — boolean. Лимит входа и сериализованного объекта запроса — 32 КиБ.

```json
{"state":{"color":"red"},"questions":{"is_red":{"instructions":"Is the color red?"}}}
```

Модель выбирается верхнеуровневым `decision_model`: это имя профиля в `models`.
Поле `provider` профиля ссылается на запись в `providers`, содержащую URL и ключ.
Отдельного блока `decision` нет; вход и аргументы CLI не переопределяют настройки.

```yaml
default_model: checks
decision_model: checks
providers:
  router:
    url: https://openrouter.ai/api/v1
    key: replace-with-api-key
models:
  checks:
    provider: router
    model: openai/gpt-6-luna
    compact_threshold: 200000
```

К базовому URL выбранного подключения добавляется `/responses`.
Профили диалога, решений и памяти могут использовать разные подключения.
Для прямого OpenAI задайте `https://api.openai.com/v1` и имя обычной модели
без префикса поставщика.

Клиент использует общий транспорт Responses API, SSE, `store: false`,
`reasoning.effort: none` и `text.format` с `type: json_schema`, `strict: true`.
Модель должна поддерживать эти параметры. Инструментов и агентского цикла нет:
один запрос, таймаут 10 секунд, без автоматического повтора. Состояние передаётся
как данные пользователя, вопросы — как инструкции оценки и описания полей схемы.
Лимит вывода рассчитывается по именам вопросов; объяснения и вероятности
не запрашиваются.

Пример успешного ответа:

```json
{"id":"resp_123","model":"openai/gpt-6-luna","answers":{"is_red":true}}
```

Поле `usage` добавляется, если провайдер его вернул. Ответ независимо проверяется
локально: нужны ровно запрошенные поля boolean, без повторяющихся ключей.
Пропущенные или лишние поля, `null`, отказ модели, неполный поток и ошибки
провайдера завершают оценку ошибкой. Автоматического перехода к другому API нет.

Без `-o` результат с переводом строки идёт в stdout; с `-o` атомарно
заменяет файл с правами `0600`, stdout остаётся пустым. Диагностика идёт
в stderr. Код 2 означает неверные аргументы, вход или конфигурацию, 1 — ошибку
провайдера или вывода, 130 — отмену. Справка не читает конфигурацию и не
обращается к сети. Команда не создаёт агентскую сессию.

## Проверка shell-команд

Клиент получает команду, workspace и Horizon home. Модель отвечает на два
булевых вопроса: `file_write` и `outside_write`. Horizon применяет режим локально:
`read` запрещает запись (в том числе при одном только `outside_write: true`),
`write` запрещает запись вне обоих каталогов, `full` пропускает оценку.

Это оценка видимого намерения команды. Модель не исследует значения переменных,
симлинки и содержимое вызываемых файлов; не проверяет соответствие поручению
или сетевые эффекты. Эти ограничения одинаковы при включённом и выключенном
рассуждении. Ошибка оценки запрещает запуск команды.

## Переход с Jev

Старый Decisions API и блок `decision` удалены. Перенесите подключения из
`provider` и `decision.provider` в карту `providers`. Для каждого профиля
задайте имя подключения в `models.<имя>.provider`; модель решений оформите
обычным профилем и укажите его в `decision_model`.
URL должен быть базовым URL Responses API. Менеджер не переписывает
пользовательскую конфигурацию. Старые блоки отклоняются строгим YAML-парсером;
отсутствующий или неизвестный `decision_model` останавливает ход `read`/`write`
до создания сессии. В режиме `full` он не нужен.

В JSON-запросах больше нет `type: noul|choice|score` и `criteria`; формулируйте
булев вопрос в `instructions`. Ответы теперь содержат непосредственно
`true` или `false`, без числовых порогов и поля `provider`.


Telegram применяет правила входного адаптера и передаёт подходящий текст в
основной ход. Решение об отправке принимает модель через инструмент Telegram.
