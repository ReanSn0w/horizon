# Horizon — решения и состояние реализации

Обновлено: 2026-09-15. Документ сохраняет согласованные решения первого этапа и отделяет их от дальнейших направлений развития. Пользовательская инструкция находится в [README.md](README.md).

## Основная идея

Horizon — самостоятельный CLI-агент на сервере. Он сам обращается к API модели, читает и изменяет файлы, выполняет shell-команды. Пользователь запускает его из shell, например по SSH, отправляет задачу и получает результат текущего хода.

Основной сценарий первого этапа — разработка в репозитории.

История сохраняется, но показывается только по запросу. Агент использует контекст чата без повторной печати старых сообщений в терминале.

Если сообщение передано аргументом, команда сразу запускает выполнение. Если сообщение поступает через перенаправленный stdin, оно читается оттуда. Если сообщение не передано и запуск интерактивный, открывается TUI для ввода одного сообщения: многострочный текст, переносы строк, перемещение курсора влево/вправо и вверх/вниз между строками. После отправки начинается обычное выполнение хода. `Enter` отправляет сообщение, `Shift+Enter` добавляет новую строку.

## Термины

- **Home** — пользовательская директория состояния Horizon, в реальности обычно `~/.horizon`. Начальная конфигурация приведена в [`config.example.yaml`](config.example.yaml).
- **Workspace** — конкретная директория запуска `resume`, которая задаёт исходную директорию выполнения инструментов. Каждый подкаталог — отдельный workspace; автоматического поиска корня Git-проекта нет. Это ограничение нужно явно описать пользователю.
- **Сессия / чат / диалог** — одна сохранённая последовательность общения с агентом. В этом проекте это синонимы; основное имя в CLI — session.
- **Turn / ход** — работа от промпта пользователя до завершения работы агента, включая промежуточные запросы API, вызовы инструментов и их результаты. Это не просто пара текстовых сообщений.
- **Генерация / выполнение хода** — текущая активная работа агента внутри сессии.
- **Форк** — новая независимая сессия, полученная копированием истории исходного чата до последнего успешного turn включительно, вместе с предшествующими неудачными попытками. Если успешных turns нет, форк пустой.

Несколько сессий означают несколько чатов. Вопрос об одновременных ходах относится к двум вызовам `resume` для одного и того же чата, а не к терминологии.

## Подтверждённые решения

### API и модели

На первом этапе поддерживаем только OpenAI Responses API. Chat Completions API и Anthropic Messages API отложены. Переключение протокола внутри существующего чата и преобразование истории между API сейчас не проектируем.

URL и ключ провайдера задаются полями `provider.url` и `provider.key` в конфиге home. Реализован Responses API без универсального слоя синхронизации разных форматов.

Именованные профили моделей (`models`) и `default_model` сохраняются. Профиль содержит `model`, `reasoning`, необязательный `score` и обязательный `compact_threshold`. Значение `score` может пригодиться для выбора модели дочернего агента; на первом этапе оно остаётся метаданной и не влияет на исполнение.

В будущем планируется навык, по которому агент сможет через shell запускать дочерних агентов. Этот навык и механизм делегирования сейчас не реализуются; обычная поддержка навыков остаётся в концепции.

### Ввод и вывод

- `resume -m 'задача'` запускает ход без редактора.
- Ввод сообщения через stdin поддерживается: например, `horizon resume < task.txt` или `cat task.txt | horizon resume`.
- `resume` без сообщения в интерактивном терминале открывает многострочный TUI-редактор: `Enter` — отправка, `Shift+Enter` — новая строка, стрелки вверх/вниз — движение по строкам.
- История доступна отдельно через `sessions read`.
- Прогресс выполнения обязательно показывается. Предусмотрены форматы ответа `text` и `jsonl`; начальный состав событий описан ниже.
- TUI нужен для ввода сообщения; обычное выполнение сохраняет модель CLI-команды.

Согласованное разделение потоков:

- `text`: итоговый ответ — в stdout; прогресс, статусы и диагностика — в stderr. Вывод в stderr сам по себе не означает ошибку.
- `jsonl`: весь структурированный поток событий, включая прогресс, результат и ошибки выполнения, — в stdout, по одному JSON-объекту на строку. Диагностика самого CLI — в stderr. Текстовое оформление не должно смешиваться с JSONL.
- Успех или ошибка выполнения обозначаются кодом возврата процесса: `0`, `1`, `2` или `130`; значения описаны в разделе CLI.

Например, `horizon resume -m 'Задача' > answer.txt` в режиме `text` сохраняет итоговый ответ в файл, оставляя прогресс видимым в терминале.

Для ввода предлагается порядок: явный `-m`, иначе перенаправленный stdin до EOF, иначе редактор в интерактивном терминале. Пустое сообщение, включая строку только из пробельных символов, — ошибка с кодом `2`. Проверка выполняется до создания сессии, изменения метаданных и записи истории; при ошибке история остаётся нетронутой. После редактора выбранный `--mode` применяется к выполнению так же, как при `-m` или stdin.

По поручению пользователя выбрана начальная детализация прогресса: в `text` показываем начало и завершение вызова инструмента — имя, путь или команду, статус, длительность; для shell также код завершения. Полные результаты инструментов показываем с `--verbose`, с обозначением сокращения длинного вывода. Краткие сообщения агента о ходе работы тоже идут в stderr, финальный ответ — в stdout.

Начальные события JSONL: `turn_started`, `progress`, `tool_started`, `tool_completed`, `compaction_started`, `compaction_completed`, `turn_completed`, `turn_failed`, `turn_cancelled`. Для ручного compact используются события compaction и `error` при неудаче. Общие поля: `type`, `timestamp`, `session_id`, `turn_id` (null для отдельной операции compact), `data`. У событий инструмента `data` содержит `call_id`, `name`, а также аргументы при запуске или структурированный результат и длительность при завершении. `turn_completed` содержит итоговый текст. Ошибки содержат `code` и `message`.

События compaction публикуются по фактически доступным сигналам API; если начало автоматического сжатия API отдельно не сообщает, его не выдумываем. При штатно обработанном завершении у запущенного turn одно конечное событие; аварийное завершение процесса может оставить поток без него. JSONL не является копией внутреннего формата истории.

### Инструменты и доступ

Подтверждённый набор инструментов модели первого этапа:

| Инструмент | Назначение |
| --- | --- |
| `file_create` | Создать файл и недостающие директории на пути к нему. |
| `file_read` | Прочитать содержимое файла. |
| `file_update` | Записать изменения отдельных фрагментов существующего файла, сохранив остальное содержимое. |
| `dir_list` | Показать содержимое директории. |
| `dir_delete` | Удалить файл или директорию. Несмотря на префикс `dir_`, работает с обоими типами. |
| `skill_read` | Загрузить основной текст навыка по имени в контекст модели. |
| `shell_exec` | Выполнить shell-команду из директории запуска `resume`. |

Термины: **инструменты** — вызываемые моделью функции, которые выполняет Horizon. **Навыки** — инструкции из `SKILL.md`; их названия и описания постоянно находятся в промпте, а текст загружается инструментом `skill_read` по решению модели.

Контракты всех семи реализованных инструментов описаны в [TOOLS.md](TOOLS.md): аргументы, результаты, ошибки, порции чтения, создание без перезаписи, рекурсивное удаление, чтение навыка и shell. Относительные пути разрешаются от workspace, абсолютные используются напрямую.

#### Редактирование фрагментов через `file_update`

Подтверждено: инструмент позволяет записывать отдельные фрагменты. Модели не требуется передавать полное содержимое файла для локального изменения.

Согласованный контракт — точная замена фрагмента:

```json
{
  "path": "main.go",
  "old_text": "port := 8080",
  "new_text": "port := 9090"
}
```

`old_text` и `new_text` могут быть многострочными. Инструмент находит точный исходный фрагмент и заменяет только его. Для вставки модель включает в `old_text` соседний текст как опору и сохраняет его в `new_text` вместе с добавлением; для удаления передаёт пустой `new_text`.

Согласованные правила: `old_text` непустой и должен встретиться ровно один раз. Если совпадений нет или их несколько, инструмент возвращает ошибку без изменения файла; модель перечитывает файл или уточняет фрагмент. Создание отсутствующего файла остаётся задачей `file_create`.

Встроенной песочницы на этом этапе нет. Агент работает с правами пользователя ОС, под которым запущен. При необходимости ограничения пользователь задаёт средствами сервера. Horizon не вводит собственных ограничений сетевого доступа.

Workspace определяет исходную директорию работы, но не ограничивает доступ пределами этой директории. Намеченный `--access workspace|full` не соответствует этому решению и не нужен в контракте первого этапа.

Каждая shell-команда стартует из директории, в которой был вызван `resume`. Например, `cd subdir && command` меняет каталог внутри этого запуска shell; следующая команда снова стартует из исходной директории `resume`.

### Инструкции и навыки

Подтверждён порядок сборки промпта модели:

```text
<Возможная вводная Horizon>
<Глобальный AGENTS.md из home>
<Список названий и описаний навыков>
<Локальный AGENTS.md из workspace>
```

Отдельную иерархию приоритетов между этими блоками не вводим. История диалога, сообщение пользователя и результаты инструментов передаются дополнительно к этому промпту. Основной текст выбранного навыка появляется как результат `skill_read`.

Инструкции из родительских каталогов автоматически не подбираются. Если `resume` вызван из подкаталога, это новый workspace со своим локальным `AGENTS.md`. Выбранное поведение: отсутствующий `AGENTS.md` пропускается; существующий, но недоступный для чтения файл даёт понятную ошибку. Оба файла перечитываются перед каждым ходом; собранный промпт сохраняет порядок во всех запросах хода, в том числе после сжатия.

`SOUL.md` исключаем из концепции. Заметки как память агента откладываем на следующий этап. Этот `IDEA.md` — рабочий документ обсуждения проекта, он не относится к памяти будущего агента.

Навыки лежат в отдельных поддиректориях `skills/`. Формат файлов — как у навыков Codex: `SKILL.md` с YAML-метаданными `name`, `description` и инструкциями; рядом могут находиться `scripts/`, `references/`, `assets/`. Основание формата: [официальная документация OpenAI](https://learn.chatgpt.com/docs/build-skills).

#### Подтверждённая модель работы навыков

- Название и описание каждого доступного навыка постоянно присутствуют в промпте модели. Каталог включается в каждый запрос к модели, в том числе внутри одного turn и после сжатия контекста; он не должен исчезать при compaction.
- Основной текст навыков заранее в промпт не включается.
- Модель сама решает, какой навык ей нужен, исходя из задачи и описаний. Пользователю не требуется выбирать навык; отдельного пользовательского механизма выбора не предусматриваем.
- Для загрузки основного текста модель вызывает специальный инструмент чтения навыка. Результат инструмента добавляется в контекст как инструкция навыка, доступная для дальнейшей работы.

Контракт инструмента: `skill_read(name)` принимает имя из каталога и возвращает основной Markdown-текст соответствующего `SKILL.md` без YAML-метаданных. Имя `skill_read` утверждено; аргументы и результат описаны в TOOLS.md. Результат содержит базовую директорию навыка для разрешения относительных ссылок.

Пример: пользователь просит проверить изменения, модель видит описание `review`, вызывает `skill_read({"name":"review"})`, получает инструкцию и выполняет проверку. Вызов инструмента и его результат сохраняются в истории хода наравне с другими инструментами.

Постоянное присутствие в промпте гарантируется именно названиям и описаниям. Основной текст становится частью рабочего контекста после вызова инструмента; если после сжатия модели вновь потребуется точная инструкция, она сможет прочитать навык повторно.

#### Предлагаемые детали реализации навыков

1. Перед каждым ходом Horizon сканирует `<Horizon home>/skills/<skill-name>/SKILL.md` и собирает каталог названий и описаний. Для первого этапа достаточно навыков из home.
2. `skill_read` разрешает имя через этот каталог. Неизвестное имя, повреждённый файл или дублирующиеся имена дают понятную диагностику; неоднозначный навык не выбирается молча.
3. Ссылки из инструкции разрешаются относительно каталога навыка. Файлы `references/` и `assets/` читаются по необходимости инструментом `file_read`.
4. Скрипт из `scripts/` запускается инструментом `shell_exec` только когда нужен для задачи. Наличие навыка само по себе не запускает его код. Исходная директория shell остаётся workspace; путь к скрипту указывается явно, при необходимости команда сама делает `cd`.
5. Навык загружается результатом инструмента. Отдельных правил приоритета для него не вводим; порядок сборки основного промпта указан выше.
6. Дополнительные метаданные вроде `agents/openai.yaml`, зависимости плагинов и установщик навыков в первый этап не входят. Поддерживаем файловый формат инструкций, а не всю инфраструктуру Codex.

Пример минимального `SKILL.md`:

```markdown
---
name: review
description: Проверка изменений кода по запросу пользователя на ревью.
---
Прочитай изменения и относящийся к ним код.
Проверь ошибки поведения и пропущенные случаи.
Сообщи найденные проблемы с указанием файлов и строк.
```

Пример обычного запроса: `horizon resume -m 'Проверь текущие изменения'`. Решение прочитать навык `review` принимает модель.

Целевая структура home первого этапа:

```text
~/.horizon/
  config.yaml
  AGENTS.md
  dialogs/
    workspaces.json
    <workspace-path-hash>/
      <session-id>.json
      <another-session-id>.json
      <session-id>.artifacts/  # полные логи инструментов
  skills/
    skill-name/
      SKILL.md
      scripts/       # необязательно
      references/    # необязательно
      assets/        # необязательно
```

### Размещение диалогов по workspace

Подтверждено: `dialogs/workspaces.json` хранит информацию о рабочих директориях, в которых работал агент. Рядом находятся каталоги workspace; имя каждого каталога — MD5 нормализованного абсолютного пути до workspace после раскрытия символических ссылок. Внутри лежат отдельные файлы сессий этого workspace.

```text
dialogs/
  workspaces.json
  <hash полного пути workspace A>/
    <session A1>.json
    <session A2>.json
  <hash полного пути workspace B>/
    <session B1>.json
```

Выбран формат отдельного JSON-файла с метаданными и структурированным содержимым для каждой сессии. Такая структура позволяет получить каталог чатов по пути workspace, перечислить его сессии и независимо блокировать каждую сессию через отдельный постоянный файл блокировки.

Алгоритм MD5 подтверждён. Согласованные правила идентификации и реестра:

- Хеш вычислять от нормализованного абсолютного пути с раскрытыми символическими ссылками, без `.` / `..` и лишних разделителей. Использовать полное hex-представление MD5 из 32 символов. Один физический каталог, открытый напрямую или через ссылку, имеет общий workspace; каждый реальный подкаталог остаётся отдельным workspace. Это же правило применяется при проверке принадлежности сессии workspace и к пути `dir` в реестре.
- В `workspaces.json` использовать `id` для хеша каталога, `dir` для нормализованного абсолютного пути с раскрытыми ссылками, `last` для времени последнего создания сессии (включая форк) или принятого `resume`. Просмотр списков, чтение истории и compact это время не меняют.
- При открытии каталога сверять сохранённый путь с текущим: совпадение хеша для разных путей должно давать ошибку, а не смешивать сессии.
- Файлам сессий дать имена по уникальным ID сессий. В метаданных сессии сохранять её ID, путь workspace и версию формата: тогда реестр workspace можно восстановить из файлов при необходимости.
- Обновления общего `workspaces.json` сериализовать отдельной короткой блокировкой; блокировка одного чата не защищает реестр от записи из другого. Не удерживать блокировку реестра во время генерации.

Следствие идентификации по пути: перенос проекта в другой каталог даёт другой хеш и считается новым workspace. Прежние диалоги остаются в старом каталоге истории; автоматическая миграция пока не предусмотрена.

#### Формат сессии: JSON с метаданными и содержимым

Подтверждено: сессия хранится как единый JSON-объект. Метаданные и содержимое находятся в одном файле; сообщения, вызовы инструментов, результаты и служебные данные API могут быть вложенными JSON-объектами. Markdown и YAML-заголовок для этого не требуются.

Согласованная общая структура (точная схема элементов API ещё определяется):

```json
{
  "format_version": 1,
  "session_id": "...",
  "workspace": "/srv/project",
  "title": "Исправление авторизации",
  "last_accessed_at": "...",
  "turns": [
    {
      "id": "...",
      "status": "cancelled",
      "items": []
    }
  ]
}
```

Метаданные также должны сохранять время создания и происхождение форка. Состояния рабочего контекста и результаты compact хранятся структурированно; точные поля предстоит определить. Формат хранения не меняет согласованный JSONL-вывод CLI.

Подтверждено: под блокировкой сессии новый JSON записывается во временный файл в том же каталоге, затем атомарно заменяет основной файл. Перед запуском инструмента сохраняется его вызов, после выполнения — результат. Если вызов не удалось сохранить, инструмент не запускается. Сбой между запуском и сохранением результата оставляет исход неизвестным. Незавершённый turn не принимается за успешный; уже сохранённые данные прерванной попытки доступны для продолжения. Детали синхронизации записи с диском и обработки оставшихся временных файлов определяются при реализации.

Подтверждено: блокировка ОС берётся на отдельном постоянном файле сессии, а не на заменяемом JSON-файле истории. Все операции, изменяющие сессию, используют одну и ту же блокировку. Файл блокировки не заменяется и не удаляется при обычных операциях, включая удаление сессии: иначе разные процессы могут заблокировать разные файлы для одного ID. Наличие файла само по себе не означает, что сессия занята. Прежнее решение блокировать непосредственно файл истории отменено.

### История и форки

Все диалоги хранятся в home. Хранилище должно содержать полное доступное клиенту состояние, необходимое для продолжения работы API, в том числе Responses API. Одного человекочитаемого текста недостаточно.

Требование к будущему формату: сохранять сообщения, вызовы инструментов и результаты, порядок элементов, связи и идентификаторы, а также нужные протоколу служебные данные, которые API возвращает клиенту. Конкретный набор полей определяется при проектировании интеграции Responses API; локальное состояние нельзя сводить к печатной истории или единственному серверному идентификатору.

Форк получает отдельную идентичность и копию истории до последнего успешного turn включительно. Предшествующие ему неудачные и прерванные попытки сохраняются, поскольку успешный ход уже мог использовать их контекст. Попытки после последнего успешного хода исключаются. Пример: успешный A → прерванный B → успешный C → прерванный D даёт форк с A, B, C. Если успешных turns нет, создаётся пустой форк. Форк чата не означает копирование файлов проекта или отдельную Git-ветку.

Предложение: `sessions read --turns N` показывает последние N ходов по определению выше, а не N пар сообщений API. Нужно отдельно решить, как при чтении отображаются инструменты и прерванные ходы.

### Сжатие контекста Responses API

Подтверждено: используем серверное сжатие контекста Responses API по порогу; дополнительно предоставляем CLI-команду ручного compact.

По [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/compaction), есть два варианта: серверное сжатие в `/responses` через `context_management` с `compact_threshold`, либо отдельный вызов `/responses/compact`. Серверное сжатие возвращает элемент compaction в потоке; отдельный endpoint возвращает новое окно контекста, которое следует передавать целиком, не вырезая его элементы. Для отдельного вызова исходное окно ещё должно помещаться в лимит модели. Зашифрованное содержимое compaction хранится без попыток интерпретации.

Решение первого этапа: серверное сжатие по настраиваемому порогу профиля модели и локальная сборка массива input. Совместимость выбранного провайдера и модели с этим механизмом необходимо проверить при реализации; одно название Responses API её не подтверждает.

Подтверждено: каждый профиль модели содержит обязательный положительный целочисленный `compact_threshold` — порог сжатия в токенах рабочего контекста. Значение задаётся пользователем под конкретную модель; общего значения по умолчанию и автоматического расчёта процента от окна нет. Порог не задаёт размер истории на диске или число turns. При выборе значения нужно оставлять запас для следующего ввода, результатов инструментов и генерации.

В хранилище различаем полный журнал и рабочий контекст для API. Сжатие уменьшает рабочий контекст, но не удаляет историю для `sessions read`. Сохраняем compaction-элементы и их положение в ходе. Успешная граница turn включает пригодное для продолжения состояние контекста.

Если ход отменён или завершился ошибкой, его сжатый контекст не принимается за успешное состояние. Следующий `resume` использует сохранённый успешный контекст и дополняет его доступной историей последующих неудачных или прерванных попыток с их статусами. Эта история не должна теряться из-за сжатия; точный способ сборки нужно согласовать с форматом API. Форк получает контекст на границе последнего успешного turn с применимым успешным compact; этот контекст может учитывать предшествующие неудачные попытки. Compaction из неудачной попытки не становится состоянием продолжения форка, даже если её записи входят в скопированную историю. Глобальный и локальный `AGENTS.md` остаются явными инструкциями нового запроса.

### Остановка и параллельность

Ctrl+C отменяет весь текущий ход: запросы к модели и выполняющиеся shell-команды вместе с дочерними процессами. Предложение реализации: управлять группой процессов каждого shell-запуска и завершать её при отмене; блокировку сессии отпускать после остановки инструментов и сохранения статуса.

Подтверждено: `resume` получает эксклюзивную блокировку ОС на отдельном постоянном файле блокировки выбранного диалога и удерживает её на всё время выполнения хода, включая сохранение результата. Два `resume` не могут одновременно выполнять ходы в одной сессии. Блокировка относится к конкретному диалогу; разные сессии могут работать независимо.

Предлагаемое поведение при занятом файле: второй `resume` сразу завершается с понятной ошибкой «сессия занята» и ненулевым кодом возврата, без ожидания в очереди. Блокировку нужно получать до чтения состояния для нового хода и освобождать при завершении, ошибке или отмене. При реализации использовать блокировку ОС, освобождаемую при завершении процесса, а не просто файл-маркер, который может остаться после сбоя.

Подтверждено: после отмены или ошибки новый `resume` начинает новый ход и получает доступную историю прерванных и неудачных попыток, включая уже выполненные инструменты и сохранённые результаты. Агенту явно сообщается, что эти ходы не завершились успешно. Это правило действует и до первого успешного turn. Прежнее решение исключать частичный контекст из следующего `resume` отменено. Форк ограничивается историей до последнего успешного turn включительно.

Вызов инструмента без сохранённого результата обозначается как имеющий неизвестный результат. Агент должен сначала проверить фактическое состояние перед повторением операции; отсутствие результата в истории не доказывает, что команда не выполнилась. При сборке контекста нужно соблюдать требования API к связям вызовов и результатов, не выдавая неизвестный исход за подтверждённый успех или ошибку.

Неудачный ход остаётся в истории с `failed` или `cancelled` для диагностики и контекста следующего `resume`, а сохранённое успешное состояние контекста остаётся прежним. Успех хода фиксируется только после завершения всего цикла агента и сохранения результата. Ошибка отдельного инструмента, которую агент обработал и после которой успешно закончил работу, не обязательно означает ошибку всего turn.

Уже выполненные изменения файлов и другие последствия команд после отмены или ошибки остаются; автоматический откат файловой системы не предусмотрен. История прерванной попытки помогает агенту учитывать эти последствия при продолжении.

### Лимиты автономной работы

Подтверждено: в настройках home предусматриваются лимит числа запросов к модели за один ход и лимит общей длительности хода. Это ограничения всего цикла агента, отдельно от таймаута конкретной команды `shell_exec`.

При достижении лимита Horizon останавливает выполнение, сохраняет доступную историю и явно сообщает причину остановки. Ход не помечается успешно завершённым. Следующий `resume` получает его доступный контекст по общему правилу прерванных попыток.

Согласованные настройки и значения по умолчанию:

```yaml
limits:
  max_model_requests: 128
  max_turn_duration: 120m
```

- `max_model_requests` — максимальное число попыток запроса к модели за ход, включая повторные запросы после сетевых ошибок. `0` отключает этот лимит.
- `max_turn_duration` — общая длительность выполнения хода, включая запросы API, инструменты и ожидание повторов. `0` отключает этот лимит. Время ввода сообщения в редакторе не относится к выполнению хода.
- Отсутствующее поле получает значение по умолчанию. Пользователь может менять оба значения в конфиге home.
- После последнего разрешённого запроса полученные вызовы инструментов выполняются и их результаты сохраняются, но следующий запрос к модели уже не начинается. Если последний разрешённый запрос штатно завершил ход, это успех; ошибка лимита возникает, когда для продолжения требуется ещё один запрос.
- По истечении общей длительности активный запрос и выполняемый инструмент прерываются. Остановка процессов и сохранение истории выполняются перед освобождением блокировки; время завершения и записи может выходить за предел длительности.
- Остановка по лимиту сохраняет статус `failed`, публикует `turn_failed` с причиной `request_limit_exceeded` или `turn_timeout` и возвращает код `1`. Статус `cancelled`, событие `turn_cancelled` и код `130` относятся к Ctrl+C.
- Автоматическое серверное сжатие внутри запроса не считается отдельным запросом. Ручной `sessions compact` — самостоятельная операция вне бюджета `resume`; к ней применяется `max_turn_duration`. При превышении длительности сохраняется прежний контекст, публикуется `error` с причиной `turn_timeout`, код возврата — `1`.

### Режимы исполнения

**Первый этап — `unit`.** Каждый запуск CLI самостоятельно выполняет один ход и сохраняет состояние. Между запусками чат остаётся на диске. Постоянный демон для первого этапа не требуется.

**Следующий этап — `server`.** Horizon работает демоном и поднимает Unix-сокет. Режим выбирается в `config.yaml` home. Команды вроде `resume` передают демону параметры запуска через сокет. Демон поддерживает несколько сессий, а из другого терминала можно посмотреть активные генерации.

В запросе к демону необходимо передавать исходную директорию `resume`, чтобы shell-команды не запускались из рабочей директории демона. Точный формат сообщений, запуск демона и подключение к потоку результата пока не определены.

## CLI-интерфейс

Реализованный интерфейс первого этапа:

```sh
horizon models
horizon resume --model chatting -m 'Посмотри проект'
horizon resume -m 'Посмотри проект и опиши его структуру'
horizon resume
horizon resume --session SESSION_ID -m 'Продолжи задачу'
horizon sessions list
horizon sessions create
horizon sessions create --fork SESSION_ID
horizon sessions read --id SESSION_ID --turns 4
horizon sessions delete --id SESSION_ID
horizon sessions compact
horizon sessions compact --id SESSION_ID
```

Реализованы глобальные `--home`, `--verbose`, параметры выбора сессии, модели и формата ответа, а также фильтры списка по workspace и активности. Без `--session` выбирается последний чат; при отсутствии чатов создаётся новый.

Подтверждено: без `--session` выбирается последняя сессия текущей директории. Если сессий нет, создаётся новая. `sessions create` сразу делает новую сессию последней, даже если в ней ещё нет успешных turns.

Продолжить сессию из другого workspace нельзя: команда завершается с ошибкой. Желательно показать путь нужной директории и готовую команду перехода, например `cd -- '/srv/project'`; путь должен быть корректно экранирован для shell. Horizon сам не меняет workspace пользователя.

Подтверждено: в каталоге workspace лежит несколько файлов сессий. Отдельный `last_session_id` не нужен: последняя сессия определяется по времени последнего обращения в метаданных этих файлов, а не по mtime файла. Метаданные каждого диалога содержат `title` и `last_accessed_at`.

Выбранное начальное правило: при создании сессии время последнего обращения устанавливается сразу; при принятом запуске `resume` обновляется после проверки сообщения, принадлежности workspace и получения блокировки. Просмотр списков, чтение истории и compact его не меняют. Новая сессия получает время строго позже существующих сессий workspace, чтобы сразу стать последней. Выбор и изменение метаданных согласуются короткой блокировкой workspace, без удержания её на генерацию. После удаления последней сессии следующая определяется из оставшихся файлов; если файлов нет, обычный `resume` создаёт новый чат.

Название хранится независимо от ID файла. Предложение начального названия: первая непустая строка первого принятого сообщения, до 80 Unicode-символов; до первого сообщения — «Новый диалог». Форк получает название исходного чата с пометкой «(форк)».

### Создание и форк

Подтверждено: отдельной команды `sessions fork` не будет. `sessions create` создаёт пустой чат; `sessions create --fork SESSION_ID` создаёт новый чат из успешного состояния исходного. Оба варианта возвращают ID созданной сессии и делают её последней в текущем workspace. Для форка источник должен принадлежать этому же workspace.

Для первого этапа выбрано: если источник занят, форк возвращает ошибку «сессия занята». Чтение состояния для копирования выполняется под блокировкой источника; исключаются только попытки после последнего успешного turn. Если успешных turns нет, история форка пуста.

### Ручное сжатие

Выбранный интерфейс:

```sh
horizon sessions compact
horizon sessions compact --id SESSION_ID
```

- Без `--id` выбирается последняя сессия текущего workspace. Если её нет, ошибка; compact не создаёт пустую сессию. Чужой workspace даёт ошибку с путём перехода.
- Используется та же эксклюзивная блокировка отдельного постоянного файла сессии, что и у `resume`. Занятая сессия даёт ошибку сразу.
- Команда вызывает `/responses/compact` для рабочего контекста последнего успешного turn с учётом последнего успешного compact. Используется профиль последнего успешного хода. При отсутствии успешных ходов операция завершается успешно без обращения к API и сообщает, что сжимать нечего.
- В запрос включаются актуальные глобальные и локальные инструкции; каталог навыков остаётся в промпте следующих запросов. Основной диалог и его история не удаляются.
- Полное окно, возвращённое compact, сохраняется как новый рабочий контекст. Отдельная служебная запись привязывает его к успешной границе чата. Это не новый пользовательский turn и не меняет последнюю выбранную сессию.
- До успешного сохранения новой записи действует прежний контекст. Ошибка API, записи или Ctrl+C сохраняет прежнее состояние продолжения. Форк включает применимое успешное сжатие; compact из неудачного хода не переносится.
- Применяется лимит длительности `limits.max_turn_duration`; ручная операция не расходует бюджет запросов какого-либо `resume`. Истечение лимита сохраняет прежний контекст и возвращает ошибку по правилам раздела «Лимиты автономной работы».
- CLI показывает прогресс в stderr и итог операции в stdout. Поддерживается `--mode text|jsonl` с согласованным разделением потоков. Если API вернул usage, можно показать его, но не обещать точный процент сокращения без соответствующих данных.

### Коды возврата

Выбраны простые коды для всех команд Horizon:

| Код | Значение |
| --- | --- |
| `0` | Команда успешно выполнена, включая успешную операцию без изменений. |
| `1` | Ошибка выполнения: API, сеть, файловая система, отсутствующая сессия, другой workspace или занятая сессия. Точная причина — в диагностике. |
| `2` | Неверные аргументы или конфигурация, включая неизвестный профиль модели. |
| `130` | Остановка пользователем через Ctrl+C. |

Код shell-команды хранится в результате `shell_exec` и не подменяет код Horizon. Если агент обработал ошибку команды и успешно завершил задачу, Horizon возвращает `0`.

### Просмотр моделей

Подтверждено: пользователь должен иметь возможность посмотреть профили моделей из конфигурации в виде таблицы наподобие `docker ps`, чтобы выбрать модель для запуска.

Предлагаемый интерфейс — `horizon models`: читает `models` и `default_model` из `config.yaml` выбранного home и печатает таблицу с заголовками и выровненными колонками, без рамок и интерактивного выбора. Запрос к провайдеру для этого не нужен.

Пример вывода с условными данными (это не реальный список доступных моделей):

```text
NAME       MODEL          REASONING  SCORE  DEFAULT
chatting   model-example  medium     100    *
coding     model-example  high       300    -
fast       model-fast     -          50     -
```

- `NAME` — имя профиля в конфиге, которое пользователь передаёт в `resume --model NAME`.
- `MODEL` — идентификатор модели у провайдера. Несколько профилей могут использовать одну модель с разными настройками.
- `REASONING` — значение из профиля; `-`, если не задано.
- `SCORE` — заданная пользователем оценка из конфига, без вычисления рейтинга командой.
- `DEFAULT` — `*` у профиля, указанного в `default_model`, и `-` у остальных.

Предложение: строки сортируются по `NAME`, чтобы порядок не зависел от обхода map. Если профилей нет, команда явно сообщает об этом. Ошибка чтения или некорректная конфигурация даёт понятную диагностику и ненулевой код возврата.

Выбор профиля для одного хода:

```sh
horizon resume --model coding -m 'Проверь обработку ошибок'
```

`--model` выбирает именованный профиль, а не произвольный идентификатор модели провайдера. Без флага используется `default_model`; явный выбор не меняет конфиг. Для неизвестного имени предлагается ошибка с подсказкой выполнить `horizon models`.

## Состояние исходников и расхождения

Первый этап реализован: CLI разбирает все перечисленные команды, выполняет цикл Responses API, семь инструментов и ручное/автоматическое сжатие, хранит сессии и артефакты, поддерживает text/JSONL и интерактивный редактор. `--access` и отдельная `sessions fork` отсутствуют согласно принятым решениям; форк выполняется через `sessions create --fork`.

`config.example.yaml` содержит режим, провайдера, профили моделей, пороги сжатия и лимиты. Workspace идентифицируется хешем реального пути, а реестр создаётся и восстанавливается из файлов сессий. `SOUL.md` и `notes/` не используются.

Автоматические и сквозные тесты подтверждают работу с контролируемым Responses-совместимым сервером и PTY. Совместимость конкретного реального провайдера проверяется отдельным opt-in тестом, описанным в [docs/responses-protocol.md](docs/responses-protocol.md).

## Открытые вопросы

Открытых вопросов по первому этапу нет. Решения по хранению, форкам, идентификации workspace, сжатию и лимитам реализованы и зафиксированы выше; внутренние форматы дополнительно описаны в `docs/`.

Доставка `Shift+Enter` зависит от терминального протокола и раскладки клавиш; совместимость и запасные способы ввода зафиксированы в [docs/terminal-input.md](docs/terminal-input.md). Поддержку сжатия конкретным endpoint следует проверять явным интеграционным тестом из [docs/responses-protocol.md](docs/responses-protocol.md).

## Граница текущей работы

Первый этап завершает Responses API, отдельный процесс на ход, файловое состояние, навыки, терминальный ввод и структурированный вывод. Другие API, демон, память в виде заметок и навык запуска дочерних агентов остаются следующими этапами.
