# Диагностика задержки первого ответа Telegram

Личное сообщение владельца проходит `shouldReply` без запроса к Jev. Telegram
запускает отдельный `horizon resume` для каждого ответа. Поэтому длительность
первого ответа после простоя нужно разделять на ожидание в очереди, запуск
Horizon, обращения к модели, инструменты и доставку.

Сопоставляйте записи локального диагностического журнала по `request_id` и
`session_id`. `message_queued` → `job_started` показывает очередь;
`horizon_resume_started` → `horizon_model_request_started` — подготовку дочернего
Horizon; пары `horizon_model_request_started/completed` — время обращения к
провайдеру; `horizon_tool_started/completed` — инструменты;
`delivery_started/confirmed` — отправку в Telegram. `horizon_resume_finished`
фиксирует полную длительность дочернего процесса. `horizon_turn_completed`
содержит только числовые `input_tokens` и `output_tokens`, если провайдер вернул
эти поля; текст ответа и полный объект `usage` в журнал не копируются.

Время обращения к модели само по себе не отделяет генерацию от возможного
автоматического сжатия провайдером по `compact_threshold`. Наличие
`horizon_compaction_completed` показывает, что сжатие произошло, но не даёт
точную длительность этой части запроса. Сравнивайте сопоставимые сессии и
размеры рабочих checkpoint; размер JSON в байтах не равен числу оплачиваемых
токенов. Отсутствие записей журнала или числового `usage` оставляет причину и
экономию неподтверждёнными.

Для проверки пользы ручного сжатия используйте отдельные тестовые сессии с тем
же провайдером. Сравните первый ответ после простоя с предварительным
`horizon sessions compact --id ...` и без него, учитывая стоимость и время
самого сжатия отдельно. Не выполняйте такой эксперимент на живой сессии ради
одного измерения: он изменит её рабочий контекст.
